心跳不是握手，日志不是 app.log

从"Raft 心跳和 TCP 三次握手是不是一回事"这个小误解出发，沿心跳 → 共识 → 协议分类 → 日志复制 → 数据同步一路走到底，看一条写请求最终如何变成多副本一致的业务数据。
2026-11-04 · 分布式概念精读 · 约 35 分钟阅读 · 写给想把 Raft 从"听说过"变成"讲得清"的工程师

学习分布式算法，常常卡在一些"听起来差不多"的词上：心跳和握手是不是一回事？Raft 日志和我天天看的 app.log 是一个东西吗？为什么说数据是"复制"的，可我在节点目录里看到的文件却各不相同、也没人来拷贝我的数据文件？

这些问题看似零散，但只要顺着它们一层层往下挖，最终会走到同一个地方——Raft 到底是怎么让多个副本上的数据保持一致的。本文就按这条路径展开：先拆掉最外层的误解，再进入 Raft 的核心机制，最后落到数据如何通过日志和快照实现同步。

一、第一个误解：TCP 三次握手不是心跳

很多人第一次接触 Raft 心跳时会下意识类比 TCP——"TCP 不也有三次握手、来回发消息确认对方在吗？那不就是心跳？"不是。两者解决的问题、发生的时机、所在的层次都不同。

TCP 三次握手

  • 性质：一次性的连接建立过程
  • 目的：同步双方初始序列号、确认收发能力正常，建立一条可靠连接
  • 时机：只在建连时发生一次，连接建好后就不再重复
  • 层次：传输层
  • 握手完成 ≠ 持续证明对方"还活着"

Raft 心跳

  • 性质：周期性、持续不断的信号
  • 目的：维持领导者权威，告诉跟随者"我还在，别发起选举"
  • 载体：可以是空的 AppendEntries RPC
  • 层次：应用层 / 分布式共识算法层
  • 只要领导者在位，就按固定间隔一直发

一句话区分：握手回答的是"我们能不能开始通信"，问一次就结束；心跳回答的是"我现在是否还活着、还是不是领导"，要反复地、周期性地回答。

网络语境里"心跳"这个词还常指另外两样东西，注意别混：一个是 TCP Keepalive（连接空闲很久后发探测包，确认对端没掉线，属于传输层保活），一个是应用层自己实现的保活。它们和 Raft 心跳形式相似——都是周期性发信号，但目的不同：Keepalive 保的是"连接"，Raft 心跳保的是"领导地位"。

概念的锚点："心跳"这个词的核心语义只有一句——周期性地发一个信号，证明"我还活着 / 我还在位"。至于在哪个层次、证明什么、断了会触发什么动作，不同系统各有设计。看清这一点，就能把形形色色的"心跳"归到同一个心智模型下。

二、同一套心跳逻辑，用在无数地方

"周期性发信号证明我还活着、一旦信号中断就触发动作"是一个极其通用的模式，从硬件到分布式系统都在用：

场景心跳怎么用信号中断后触发什么
高可用集群 / 故障转移主备节点间用心跳线周期性互探备节点判定主节点故障，接管服务
操作系统 / 进程监控被监控服务定期喂狗（喂 watchdog）systemd 等判定服务假死，重启它
网络设备 / 网关协议VRRP 在主备交换机间发通告心跳备机升级为主，避免网关单点
容器编排 / 分布式调度节点周期性上报自身状态（Kubernetes node lease/heartbeat）控制面摘除失联节点，迁走其上负载
底层硬件 / 时钟处理器内部定时心跳、多核全局计时器同步作为芯片各部件协调推进的节拍

从这个表能看出，心跳模式有两个共同部件：一个周期性的信号源，和一个"超时未收到即判定异常"的监听方。Raft 心跳正是这个通用模式在共识算法里的实例——只是它"超时后的动作"比较特别：不是简单重启或接管，而是跟随者发起一次新的选举。

三、Raft 到底解决什么问题

Raft（论文：Ongaro & Ousterhout, In Search of an Understandable Consensus Algorithm, 2014）被设计出来的首要目标不是最强，而是可理解——它把复杂的分布式共识拆成几个相对独立、可以分别讲解的子问题。心跳正是其中"领导者选举"的一个零件。

图 1：Raft 把共识拆成四个可以分别理解的子问题

本文沿着从外到内的顺序，最终重点落在第 ② 个——日志复制，因为它直接回答了"数据怎么变一致"。但在那之前，先把第 ① 个里两个最容易被问到的概念讲清楚：任期和选举超时。

四、任期是逻辑时钟，不是物理时长

Raft 里的 Term（任期）是一个单调递增的整数，每开始一次新的选举就加一。它的作用相当于一台逻辑时钟——用来分辨"谁的信息更新"，而不是用来衡量物理上过了多少秒。

一个节点看到更高的任期号，就知道对方代表的是"更新的一个时代"，于是主动让位、更新自己的任期。这样 Raft 不需要全局同步的物理时钟，仅靠这台逻辑时钟就能识别过期的领导者和旧请求——Term 衡量的是"先后"，不是"长短"。

真正在工程中和物理时间相关、也最需要调校的，是选举超时（election timeout）：跟随者在这么久没收到心跳后，就认为领导者可能挂了，转而发起选举。这里有一组常被引用的数字：

参数典型值说明
etcd 心跳间隔默认 100ms领导者多久发一次心跳
etcd 选举超时默认 1000ms跟随者多久没收到心跳就发起选举（官方 tuning 文档口径）
学术上的选举超时约 150–300ms，且随机化Raft 论文建议在一个区间内随机取值

来源：etcd 官方文档 tuning 章节（heartbeat interval 100ms、election timeout 1000ms）；随机化区间的建议来自 Raft 论文。具体数值随版本与部署环境而变，跨城/高延迟场景需另行调大。

选举超时的设置遵循几条原则：

  • 远大于网络 RTT 和一次持久化的耗时，否则正常的网络抖动会被误判成领导者挂了；
  • 通常至少是心跳间隔的数倍，保证中间能漏掉几次心跳也不立刻重选；
  • 必须随机化：让各个跟随者的超时错开，避免大家同时抢主导致选票平分——随机化是 Raft 简单而关键的设计；
  • 是一个权衡：太短，频繁重选、系统抖动；太长，领导者真挂了之后恢复得慢。

五、插曲：通信协议到底分几类

讲到这里容易发散到一个更大的问题——Raft 算哪门子"协议"，它和 TCP、HTTP、gRPC 是什么关系？简单做个分类，有助于定位 Raft 的位置：

分类层面典型协议回答的问题
网络 / 传输层TCP、UDP；IP、ICMP、ARP数据怎么在网络上可靠/不可靠地传
应用层（通用）HTTP、DNS、SMTP通用应用之间如何交换报文
API / 程序调用REST、GraphQL、gRPC；MQTT、AMQP程序之间"怎么调接口 / 怎么收发消息"
分布式共识Paxos、Raft、2PC多个节点如何对同一件事达成一致
特定领域 / 硬件Modbus、OPC、PROFINET工业设备等专用场景的通信约定

所以 Raft 是一种分布式共识协议：它通常跑在 TCP 之上（用 TCP 保证基本的可靠传输），通过自己定义的 RPC（RequestVote、AppendEntries）在应用层达成多节点共识。TCP 管"消息别丢、按序到"，Raft 管"即使节点会挂、网络会抖，哪些日志算数、按什么顺序生效"——两者是上下层协作，不是一回事。

六、进入正题前：领导者的带宽为什么更高

在看日志复制之前，先有一个直观的工程现象：Raft 集群里领导者的网络和负载通常明显高于跟随者。原因正是它要承担"复制中心"的角色：

领导者：大量出站

  • 扇出复制：一条日志要发给 N−1 个跟随者
  • 周期性心跳：持续向所有节点发送
  • 客户端请求集中：所有写入都汇聚到领导者
  • 快照传输：给落后节点发快照时的瞬时高峰

跟随者：主要是入站

  • 被动接收日志和心跳
  • 返回的确认响应非常小
  • 不主动发起复制
  • 流量结构明显不对称

这种不对称可以通过工程手段缓解：Follower Read（读请求分摊到跟随者，注意一致性处理）、日志和心跳的批处理与流水线、以及Multi-Raft 分片（把数据切成多个 Raft 组，让不同组的领导者分散在不同物理机上，互相分摊压力）。理解了"扇出"这个特征，就自然理解了为什么需要 Multi-Raft。

七、第二个关键澄清：Raft 日志不是 app.log

这是和"心跳/握手"并列的另一个高频误解。Raft 里反复出现的"日志（log）"，和你在服务器上 tail -f app.log 看的那个日志，同名但完全是两种东西。

Raft 日志

  • 装的是状态机指令，例如 PUT key=foo value=bar
  • 每条含：索引 index、任期号 term、命令 command
  • 是序列化后的"待执行操作指令"
  • 用途：在多副本间复制、参与状态恢复
  • 是达成一致性的核心数据结构

业务本地日志 app.log

  • 装的是程序运行的文本记录
  • 给人看的：错误堆栈、关键事件、调试信息
  • 是"已经发生之事"的描述
  • 用途：调试、审计、监控、排障
  • 不参与状态恢复，重放它无法重建数据
# Raft 日志大致长这样（伪结构）：每条是一条"操作指令" index=42 term=3 command="PUT key=foo value=bar" index=43 term=3 command="DEL key=old" index=44 term=3 command="PUT key=cnt value=9" # 而 app.log 长这样（给人看的文本）： # 2026-11-04T10:00:01 INFO request handled path=/v1/kv status=200 # 2026-11-04T10:00:02 ERROR downstream timeout, retrying...

一句话记住区别：Raft 日志是"待执行、待同步的操作指令清单"，重放它能精确重建状态；业务日志是"程序运行过程的文字记录"，只是给人看的旁证。这条区分是理解后面所有内容的前提。

八、日志复制与业务数据：复制的是"操作"，不是"数据文件"

现在可以正面回答最初那个问题了：业务数据到底是怎么被"复制"的？先明确 Raft 日志里装的指令范围——它复制的是"会改变状态的操作指令"，既可以是元数据操作，也可以是业务数据操作。也就是说，业务数据的变更通常正是通过 Raft 日志来复制和达成共识的。

一条写请求的完整旅程如下：

变成日志条目：客户端写请求（如 PUT foo=bar）到达领导者，被编码成一条 Raft 日志条目。
复制到多数派：领导者把这条日志并行发给所有跟随者，各节点先持久化到本地日志。
多数确认后提交：当超过半数节点（含领导者）确认写入，这条日志被标记为 committed——这一刻它才算"生效"。
按序应用到状态机：各节点按相同的全局顺序，把已提交日志应用到本地状态机（etcd 用 BoltDB，TiKV 用 RocksDB），于是在 data 目录产生出相同的数据。
返回客户端：领导者应用成功后向客户端返回成功。
图 2：日志复制（发给多数派）→ 提交（共识）→ 应用到状态机；注意节点间传输的是日志，不是数据文件

这里有一个精确的表述值得记住，它厘清了 Raft 和存储引擎的分工：

Raft 管的是"业务数据变更的复制与共识"，而不是"业务数据的物理存储与查询"。Raft 决定"哪条变更算数、按什么顺序生效"；真正把数据写进磁盘、提供查询的是下层状态机（BoltDB / RocksDB）。两者是协作关系，不是割裂关系。

九、"复制"和"共识"分别指什么

这两个词经常连着说，但它们是两件不同的事：

复制 Replication

把变更操作编码成日志条目，并行发送给所有跟随者，确保至少有多数节点把这个变更提议记录下来。

关注：这条日志有没有在足够多的节点上存下来。

共识 Consensus

多数派确认才生效（committed），所有副本按相同的顺序应用，保证状态机一致。

关注：这条变更在全局顺序里处于什么位置、何时才算数。

合起来看完整闭环：一条写请求先变成日志条目被复制到多数节点，多数确认后按全局统一顺序提交并应用（共识），最终所有副本的业务数据状态保持一致。复制是"让足够多的节点看到同一条指令"，共识是"大家就这条指令的生效与顺序达成一致"。

十、data 目录的数据：是"算"出来的，不是拷贝来的

最后回到那个最具体的困惑：我在每个副本的 data 目录下都看到了数据，那是不是有谁把数据文件复制过来了？不是。数据的产生是一个两阶段过程，节点之间真正传输的始终是日志和快照：

日志复制阶段：变更指令先写入 Raft 日志，复制到多数节点并持久化，多数确认后提交。
状态机应用阶段：各节点按相同顺序执行已提交的日志指令，在本地 data 目录"计算"出相同的数据（etcd 写入 BoltDB，TiKV 写入 RocksDB）。

所以 data 目录里的数据，是每个节点用同一份日志、按同一顺序各自执行后得到的结果——因为输入（日志）和顺序完全相同，状态机又是确定性的，结果自然一致。这比直接拷贝数据文件更可靠：直接拷贝二进制文件无法处理"拷贝到一半、版本不一致、文件损坏"等问题，而"日志 + 确定性重放"能精确保证一致。

落后节点怎么追：快照 + 日志

如果一个节点宕机很久、落后了成千上万条日志，一条条补太慢。Raft 的做法是快照（Snapshot）：

  • 领导者把自己某一时刻的状态机整体打成快照，发给落后节点；
  • 跟随者用快照替换本地状态，先快速追到快照点；
  • 然后从快照点之后继续同步日志，把快照之后的新变更补上。
图 3：落后节点先用快照快速对齐，再续传快照点之后的日志
最终的本质：节点之间真正在网络上传输的，是日志（逐条指令）和快照（某个时点的整体状态），从来不是直接拷贝 data 目录里的数据文件。每个副本上的业务数据，都是它"重放日志 / 加载快照后续传日志"自己计算出来的结果。

结语：从一次"听不懂"，到讲清整条数据流

回头看这条学习路径，最初只是一个小疑问——"心跳是不是握手"——但顺着它一层层走，竟然串起了 Raft 的大半内容：

  • 心跳不是握手：握手问一次"能不能开始"，心跳周期性证明"我还在位"；
  • 任期不是时长：它是分辨先后的逻辑时钟；选举超时才是需要按 RTT 调校的物理参数；
  • Raft 日志不是 app.log：前者是可重放的状态机指令，后者是给人看的运行记录；
  • 复制不是拷贝数据文件：节点间传的是日志和快照，data 目录的数据是各副本按相同顺序"算"出来的。

把这四组"看似一样、实则不同"的概念分清，Raft 就不再是一堆名词，而是一条清晰的数据流：写请求变成日志 → 复制到多数派 → 多数确认后按统一顺序提交 → 各自应用到状态机 → 多副本数据一致；落后者用快照先对齐、再续传日志。

很多时候学不懂一个技术，不是因为它难，而是被几个"同名异物""形似实异"的词挡在了门外。一旦把这层窗户纸捅破——就像分清心跳和握手、日志和日志——后面的机制反而顺理成章。这大概也是学习一切复杂系统时最值得复用的方法：先在概念的边界处停下来，问一句"它们真的是一回事吗"。
