AI 正在重写软件系统依赖的协议

网络从主机互通变成 collective-aware fabric，推理从无状态 HTTP 变成 KV Cache 与会话管理，Agent 把工具、任务、授权、审计和持久执行推向新的基础设施层
2026-11-10 · 分布式系统与 AI 基础设施 · 约 41 分钟阅读 · 写给架构师、平台工程师、QA 与正在建设 Agent 系统的团队

过去一年，很多人讨论“AI 提升了多少编码效率”。这当然重要，但它还不是最深的变化。更深的变化发生在软件系统平时默认依赖的那些协议上：网络如何传、状态放在哪、请求持续多久、工具如何调用、权限如何委托、失败如何恢复、动作如何审计。

传统 Web 系统的默认假设很清晰：客户端发一个 HTTP 请求，服务端尽快返回一个完整 JSON；应用层尽量无状态，状态放进数据库或缓存；服务之间通过 RPC 通信；身份由登录态、API key 或服务间凭证保证。大模型系统把这些假设逐一拉长、拆开，甚至倒过来重排。

训练侧，一个 job 需要成百上千甚至上万张加速器同时存活，主要流量不是零散 RPC，而是 AllReduce、AllGather、ReduceScatter、AllToAll 和 MoE expert dispatch。推理侧，一个请求会在 GPU 显存里维护持续增长的 KV Cache，并可能跨 prefill 与 decode 两个资源池迁移。Agent 侧，模型不再只是输出文本，而是选择工具、发起调用、等待审批、接收结果、再决定下一步。

本文的核心判断：AI 没有催生一个可以解决所有问题的“万能 Agent 协议”。它真正推动的是协议栈重新分层：collective-aware fabric、KV-aware inference runtime、MCP/A2A 互操作、durable execution、外部授权审计和 GenAI observability 必须组合使用。

一、先看全景：为什么一个协议已经不够用了

“协议”这个词容易被理解得太窄。很多团队一提到 AI 协议，就只问 MCP 是什么、A2A 是什么、OpenAI API 怎么调。可是从系统角度看，一次模型请求至少穿过下面这些层次，而每一层都有不同的协议问题。

图 1：AI 系统协议栈不是一条协议，而是一组分别承担连接、状态、协调、信任和观测的层次

这些层次回答的是不同问题：

如何说话

由 HTTP、gRPC、JSON-RPC、SSE、WebSocket、RDMA verbs 等承担，定义消息如何编码、传输、流式返回。

谁在说话

由 OAuth/OIDC、mTLS、SPIFFE/SPIRE、API key、工作负载身份等承担，定义用户、Agent、工具和服务的身份。

状态在哪里

由 GPU 显存、KV Cache、checkpoint、对象存储、并行文件系统、向量数据库和共享日志承担。

动作是否可靠

由 durable workflow、事务、幂等键、重试、超时、补偿、审批和回滚机制承担。

因此，MCP 不能自动解决授权，A2A 不能自动解决事务，SSE 重连不能证明工具副作用没有发生，UEC 规范发布也不能直接等同于多厂商大规模生产成熟。协议栈必须分层设计、分层验证。

二、训练网络：从“通用主机互联”到 collective-aware fabric

传统数据中心网络的主要目标，是让大量主机通过通用协议可靠互联。即使存在 RPC、短连接、shuffle、南北向流量和局部拥塞，网络本身通常不需要理解某个应用层同步原语。大模型训练改变了这一点。

2.1 一个 rank 停顿，为什么会拖垮整个 job

大模型训练通常组合多种并行策略：data parallel 将数据样本切到多个 rank，tensor parallel 在层内切分权重和算子，pipeline parallel 将不同层放到不同 stage，expert parallel 在 MoE 模型中把专家分布到不同设备。一个 rank 失败或慢下来以后，参与同一个 collective 的其他 rank 无法独立越过当前 step。

这与普通 Web 服务很不一样。普通服务中一个副本变慢，负载均衡可以把新请求导走；训练中一个 rank 停顿，其他所有 rank 都可能在同步点等待。故障成本因此变成：

故障检测时间 + 节点替换或重排队时间 + 通信域和训练进程初始化时间 + checkpoint 读取和 resharding 时间 + checkpoint 之后计算的重放时间 ——大模型训练中的故障成本不是“修一张卡”，而是整个 gang 的停顿成本

Meta 关于大规模机器学习研究集群可靠性的论文显示，硬件归因故障影响的 job 比例并不高，但会显著影响 GPU runtime；job 使用的 GPU 数越多，MTTF 越短。这类数据的重要性在于，它把“故障是异常事件”的传统观念改成了“故障是大规模训练内的常态条件”。

2.2 集合通信原语决定网络行为

集合通信原语典型用途网络行为主要风险
AllReduce数据并行梯度同步周期性强，同步边界明确；ring/tree 路径常见慢节点、链路热点、尾延迟
ReduceScatterZeRO/FSDP 等状态分片先归约再分散，常与 AllGather 组合路径组织与分片不均

NCCL 位于训练框架和底层网络之间：对上给 PyTorch、Megatron 等框架提供集合通信 API；对下使用 NVLink、shared memory、InfiniBand verbs、RoCE、socket、NetworkDirect 或插件；内部根据拓扑、消息大小、rank 数量和平台能力选择 ring、tree、CollNet、NVLS、PAT 等算法。

2.3 Scale-up 与 scale-out 是两个问题

AI 集群常被笼统称为“高速互联”，但实际上 scale-up 和 scale-out 的设计目标不同。Scale-up 关注一个服务器、机架或 pod 内几十个加速器的高带宽、低延迟、内存语义和可能的缓存一致性；scale-out 关注跨机架、跨集群、大量端点的路由、拥塞、故障域、队列和可扩展性。

层级代表技术适合通信关注点
Package / serverHBM、PCIe、CXL、NVLink-C2C本地 CPU/GPU、内存扩展带宽、延迟、一致性
Rack / pod scale-upNVLink/NVSwitch、UALink、ICITensor parallel、小规模 AllToAll全互联、故障域、内存语义
Multi-rack scale-outInfiniBand、RoCE、UECData parallel、跨 pod collective路由、拥塞、容错、扩展
跨站点WAN、多集群调度容灾、混合云、异地协同广域延迟、安全域、一致性

NVLink/NVSwitch 是强垂直整合方案；UALink 面向开放加速器 scale-up；CXL 重点在 coherency、memory semantics 和内存池化；UEC 更偏 AI/HPC scale-out fabric。把它们说成彼此完全替代，会丢失各自真正解决的问题。

三、InfiniBand、RoCE 与 UEC：没有单一赢家

关于 AI 网络，行业里常有两种过强说法：一种认为大规模训练必须使用 InfiniBand，另一种认为以太网会很快全面替代一切。公开的系统实践更接近第三条结论：多条路线并存，而且超大规模云厂商往往使用深度定制传输。

3.1 InfiniBand 的优势与边界

InfiniBand 长期服务 HPC，在 RDMA verbs、硬件可靠传输、低延迟、自适应路由、子网管理、网内计算和 AI/HPC 软件生态方面积累完整。它的优势不是“端口带宽高”这一项，而是端到端栈成熟。

边界也同样清楚：它通常意味着更集中的生态、专用设备、特定管理体系和成本结构。对希望复用现有以太网运维、交换和多供应商生态的组织来说，RoCE 或 UEC 更有吸引力。

3.2 RoCEv2：把 RDMA 放进 IP/UDP，复杂性转移到无损与拥塞层

RoCEv2 使用 IP 和 UDP 封装 RDMA 语义，支持三层路由。它保留了以太网基础设施，但对以下机制高度敏感：PFC 是否产生暂停风暴或死锁，ECN 标记是否及时，DCQCN 参数是否匹配 RTT，QP、NIC 队列、ECMP hash 和多路径是否匹配集合通信模式。

注意：RoCEv2 的难点不是“RDMA 能不能跑在以太网上”，而是在微秒级 RTT、同步训练和突发大流中保持低拥塞、低尾延迟，并能快速定位故障和恢复。

Meta 在 SIGCOMM 2024 的 AI training over Ethernet 实践说明，在严格工程控制、网络部署和上层集合通信库协同下，以太网 RDMA 可以支撑大规模训练。该经验的价值不是证明“以太网无条件优于 InfiniBand”，而是证明路线选择依赖运营能力、拓扑、拥塞控制和软件栈协同。

3.3 UEC：从 PFC 依赖走向现代 AI Ethernet

Ultra Ethernet Consortium 针对 AI/HPC 负载重构以太网传输体系。公开规范和材料强调 packet spraying、selective retransmission、adaptive multipath、sender window、receiver credit、端到端拥塞控制、遥测、多路径和可扩展 fabric。

这背后的趋势是：不再简单依赖 PFC 在整条链路上构造“全局无损”，而是通过更细粒度的传输、拥塞反馈、多路径分发和选择性恢复，降低 PFC 可能导致的 head-of-line blocking、拥塞传播和死锁风险。

但标准发布与大规模生产成熟是两件事。UEC 要真正成为跨厂商基础设施，还需要网卡、交换机、GPU 平台、拥塞控制、集合通信库、运维工具和故障定位体系经过多代互操作验证。

3.4 前沿办法及代价

四、推理协议：无状态 HTTP 为什么不够了

传统在线服务的一个理想状态是应用层无状态：任何一个副本都能处理请求，状态保存在数据库、缓存或对象存储中。LLM 推理不同，它在 GPU 显存里持有 KV Cache，并在请求生命周期内持续增长。推理服务因此从“请求转发系统”变成“显存内状态管理系统”。

4.1 从完整响应到流式 token

一个普通 HTTP API 的模式是：

HTTP Request → complete JSON Response

LLM 推理更常见的是：

HTTP/JSON Request → SSE token events → final completion event

SSE 提供服务器到客户端的单向事件流、浏览器自动重连和 Last-Event-ID。它适合逐 token 输出、进度更新和长响应。但 WHATWG 的 SSE 标准本身不定义执行恢复、事务、幂等、应用层背压、工具副作用或服务端会话迁移。

因此，客户端断线后重新连上，只说明传输层重新建立，不说明：

  • 模型是否已经完成生成；
  • 工具调用是否已经产生副作用；
  • 请求是否应该重试；
  • 重试会不会重复执行；
  • 服务端是否仍保留该请求的 KV Cache；
  • 客户端能否从某个 token 或某个工具步骤继续。

4.2 Orca：调度粒度从 request 变成 iteration

Orca 指出，自回归生成模型不是在一次完整 batch 中处理完所有请求，而是在多个 iteration 中持续生成。Orca 因此提出 iteration-level scheduling 和 selective batching：调度器在每个 iteration 决定哪些请求参与计算，而不是假设一个请求从进入到完成都固定在同一个 batch 中。

这给后续系统奠定了共同方向：推理调度不再只是负载均衡器把请求发给某个副本，而是进入运行时内部，与 batch、KV Cache、生成长度、排队延迟和 SLO 联动。

4.3 PagedAttention：KV Cache 像虚拟内存一样分页

Transformer decoder 在生成每个 token 时需要之前 token 的 key/value。若每次重新计算历史 token，成本会随上下文长度增长；系统因此把 KV 张量保存在 GPU 显存中。问题是请求长度和生成长度不可完全预测，连续预留会造成碎片。

vLLM 的 PagedAttention 借鉴操作系统虚拟内存和分页机制：KV Cache 以固定大小 block 管理，逻辑连续块可以映射到非连续物理块，并支持 copy-on-write sharing。它解决的不是模型算法，而是推理内存管理。

4.4 SGLang：公共前缀成为可复用资源

SGLang 的 RadixAttention 关注公共前缀 KV Cache 的复用。系统提示词、公共文档、多轮对话、结构化输出和 Agent 子任务经常共享前缀，如果路由和上下文组织能命中已有 KV，就可以减少重复计算。

这也改变了网关职责。普通网关只看 URL、header 和副本健康状态；推理网关还可能关心模型版本、LoRA adapter、会话上下文、前缀位置、KV 容量、TTFT、TPOT 和请求迁移。

五、Prefill / Decode 分离：KV Cache 成为跨资源池状态

如果说 PagedAttention 解决的是单个推理引擎内的 KV Cache 管理，那么 DistServe、SplitWise 和 Mooncake 推进的是更下一层：prefill 与 decode 的资源需求不同，可以拆分到不同资源池，KV Cache 需要在资源池之间迁移。

5.1 两个阶段的瓶颈为什么不同

阶段计算特征主要瓶颈资源策略
Prefill一次性处理大量输入 token，矩阵乘 batch 大算力、长上下文峰值、TTFT、排队延迟高算力 GPU、独立资源池、chunked prefill
Decode逐 token 自回归生成，每次迭代计算量较小HBM 带宽、KV Cache、TPOT、batch 组织内存带宽友好、大 batch、独立 decode 池
KV transfer把 prefill 产生的 KV 迁移给 decodeNIC、CPU、序列化、缓存容量和尾延迟RDMA、统一索引、引用管理和 connector

DistServe 的系统结论是：把 prefill 和 decode 合并部署会互相干扰，拆分后可以分别优化资源并提升 goodput。SplitWise 进一步强调不同阶段可以匹配不同硬件。Mooncake 则把 KV Cache 作为中心对象，利用 GPU 集群外的 CPU、DRAM、SSD、NIC 构建分离式缓存层。

图 3：KV Cache 从单引擎内状态变成跨 prefill、decode、缓存层流动的对象

5.2 最大缺口：没有开放可移植 KV 格式

尽管 KV Cache 已成为推理系统的中心资源，但公开证据不足以支持“跨厂商统一线格式已经形成”。vLLM、SGLang、TensorRT-LLM、Mooncake 等系统都在管理 KV，但张量布局、块粒度、传输 connector、引用方式、缓存层级和引擎内部状态并不天然一致。

工程含义：当前可以依赖引擎内分页、前缀复用和显式 connector 优化 KV，但不应假设一个引擎生成的 KV 能无转换地被另一个引擎消费，也不应假设 KV transfer 本身就是事务性、可恢复的。

5.3 推理网关标准化的是扩展点，不是全部语义

Kubernetes Gateway API Inference Extension 通过 Envoy External Processing Protocol 扩展网关，核心资源包括 InferencePool 和 InferencePoolImport。它的目标是标准化推理工作负载的路由扩展点，让网关可以根据推理后端能力做更合适的路由。

但它不是统一模型格式，不定义 KV Cache 线协议，也不完整规定 Agent 工具调用、事务、审批、审计或会话迁移。把推理网关误认为完整 Agent 基础设施，会造成架构上的过度假设。

六、MCP 与 A2A：工具连接和任务委托不是一回事

Agent 生态中最常被放在一起比较的是 MCP 和 A2A。但它们解决的问题处在不同层次。MCP 让模型宿主连接工具和上下文；A2A 让独立 Agent 之间协作和委托任务。

6.1 MCP：模型宿主、客户端和工具服务器

MCP 的基本结构是 host/model application、MCP client 和 MCP server。Host 是模型应用，client 负责与某个 server 建立连接，server 暴露 resources、tools、prompts 或其他能力。MCP 使用 JSON-RPC 编码消息，但 JSON-RPC 本身只是传输无关的消息格式，不提供 MCP 的会话生命周期。

2025-06-18 版定义了 stdio 和 Streamable HTTP 两种标准传输：stdio 适合本地子进程，Streamable HTTP 通过一个支持 POST 和 GET 的 HTTP endpoint 通信。对于请求，服务端可以返回单个 JSON，也可以返回 text/event-stream。有状态会话可以通过 Mcp-Session-Id 标识。

规范中的几个边界非常重要：

  • 断线不应被解释为取消；取消应显式发送 CancelledNotification；
  • Last-Event-ID 用于 SSE 消息重放，不代表会话状态恢复；
  • Streamable HTTP 可流式返回，但不自动提供事务提交或回滚；
  • MCP server 不能默认读取完整对话，也不应默认探测其他 server；
  • Host 需要负责权限、客户端隔离、上下文聚合和用户边界。

6.2 A2A：面向独立、可能不透明的 Agent

A2A 的设计前提是：协作双方可能由不同框架、语言或厂商构建，也不共享内部状态、记忆或工具。因此它通过 Agent Card 声明身份、技能、端点和安全方案，通过 Task 管理工作单元，通过 Message、Part 和 Artifact 表达输入、内容与结果。

A2A 1.0 的权威数据模型由 a2a.proto 定义，并提供 JSON-RPC、gRPC 和 HTTP/REST 绑定。它支持同步、流式、异步任务、推送通知和长任务管理。

需要注意幂等边界。A2A 规范中，Cancel Task 要求幂等；Send Message 可以通过 messageId 检测重复，但这不等同所有消息天然 exactly-once，也不保证远程 Agent 的工具副作用自动去重。跨 Agent 的重复提交和副作用仍需要应用层或持久工作流处理。

6.3 二者如何组合

协议核心问题典型路径不解决什么
MCP模型宿主如何连接工具、资源和提示Host → MCP Client → MCP Server → Tool/Data不自动提供完整事务、安全策略或跨 Agent 协作
A2A独立 Agent 如何发现能力、委托任务、交换产物Client Agent → Remote Agent → Task / Artifact不共享内部工具，不保证所有副作用 exactly-once
Durable Workflow长任务如何持久化、等待、审批、重试和恢复Workflow + Activity + History不自动让第三方 API 变幂等或事务性

一个典型系统可能同时使用三者：Agent Orchestrator 通过 MCP 连接文件、数据库、搜索、工单等工具；遇到专业子任务时通过 A2A 委托给另一个独立 Agent；整个长流程由 Temporal 一类 durable execution 承载状态、审批、超时、重试和恢复。

七、数据、存储、Checkpoint 与 RAG：状态语义正在分裂

AI 系统中的状态不再只有“业务数据库里的权威数据”这一类。权重、checkpoint、KV Cache、embedding、vector index、intermediate activation、训练样本和检索结果具有不同的持久性、可重算性和一致性要求。协议设计必须先区分状态类型，而不是对所有状态使用同一种事务模型。

7.1 AI 数据路径的新负载

负载访问模式主要风险
Data preparationSort、shuffle、混合读写、大量中间结果聚合带宽不足、阶段屏障拖慢
Dataloader大量 worker 随机读取小到中块，数据常只读一次GPU 等数据，页缓存命中率低
Checkpoint save周期性 TB 级突发大写与训练通信、前台 I/O 冲突
Checkpoint load全量读取并 reshardRTO 高，并行拓扑变化带来转换成本
KV Cache随机读写、迁移、驱逐、复用热点、GC、跨阶段传输成本
Vector index构建、更新、删除、压缩、检索新鲜度、召回率和重建成本难兼顾

7.2 3FS：AI workload 驱动的并行文件系统

DeepSeek 3FS 面向 data preparation、dataloaders、checkpointing 和 KVCache。公开材料显示，它采用 disaggregated architecture，支持 locality-oblivious 访问，使用 CRAQ 强一致复制、RDMA、现代 NVMe SSD、文件接口和事务 KV 支撑的元数据层。

官方 README 中最常被引用的指标，是 180 个存储节点在训练背景流量下实现约 6.6 TiB/s 聚合读。引用这个数字时必须保留条件：它来自 DeepSeek 指定硬件、网络、节点配置和测试场景，并非第三方在任意环境下的独立复测。

3FS 的关键价值不是重新发明了 CRAQ 或 RDMA，而是把已有强一致复制、SSD、高速网络和文件接口围绕 AI 全数据路径进行端到端整合。它应被定位为有真实生产背景的开源系统突破，而不是未经限定的通用文件系统理论革命。

7.3 Checkpoint 从存盘变成状态迁移协议

ByteCheckpoint 的关键设计是 parallelism-agnostic checkpoint representation 和 load-time resharding。它让 checkpoint 不再只是崩溃后恢复所需的文件，而成为模型状态跨并行策略、GPU 数量、训练阶段、评估任务和存储后端迁移的协议层。

Universal Checkpointing 也将 checkpoint 与 tensor parallelism、pipeline parallelism、sequence parallelism、ZeRO distributed training 等策略解耦，使训练可以在不同硬件配置和并行策略之间重配置。

但截至 2026 年，还不能说已经形成跨所有框架、覆盖 optimizer state、scheduler state、RNG state、parallel topology、shard mapping 和完整运行时状态的中立统一标准。Safetensors 解决的是 tensor 安全分发与加载，避免 pickle 任意代码执行风险，但不等同完整训练 checkpoint。

7.4 RAG：不是写入向量库就结束

生产 RAG 的完整链路包括源数据库变更捕获、文档解析和切块、embedding、向量写入、索引更新、hybrid search、metadata/ACL 过滤、rerank 和上下文组装。系统问题集中在新鲜度、权限和索引版本，而不只是向量检索是否快。

常见路径是 CDC 与消息系统捕获源库变化，再触发 chunk、embed 和索引更新。Debezium 官方文档说明其默认提供 at-least-once；在 Kafka Connect 中可以结合 Kafka transactions 使用 exactly-once 支持。但端到端保证还取决于 sink 幂等、offset 提交、schema 变化、索引提交、失败恢复和 embedding 版本管理。

不要把链路各组件能力直接相加：“Debezium 可接 Kafka”“Kafka 有事务”“向量库支持写入”不能自动推出 source DB → chunk → embed → vector index → ACL 的端到端 exactly-once 已经无条件成立。

7.5 派生状态更适合版本化发布，而非逐条长事务

KV Cache、embedding、vector index 和 materialized result 多是可由源数据和权重重算的派生状态。丢失它们通常主要影响性能，不一定影响权威数据正确性。因此更自然的工程模式是：

后台构建新一代状态 → 校验质量、召回率和延迟 → 原子切换 metadata pointer → 保留旧版本用于回滚

这与 Iceberg 的 snapshot、manifest、metadata pointer 和 optimistic concurrency 思想相似：不是对每个对象逐个做长事务，而是用不可变文件、元数据图和原子指针发布形成版本边界。不同产品对原子切换、alias、多租户、权限和回滚的支持程度不同，需要逐项验证。

八、信任边界：Agent 的授权不能交给模型自己判断

传统系统的授权链路主要是“用户—应用—数据库/内部 API”。Agent 系统把这条链路拉成“用户—Agent Orchestrator—LLM Provider—MCP Tool—第三方 API—其他 Agent”的动态委托链。谁代表谁行动、令牌能访问什么、动作是否可撤销，都必须显式表达。

8.1 动态委托链需要回答的问题

  • 当前动作代表哪个用户；
  • 运行 Agent 的工作负载身份是什么；
  • 令牌能用于哪个资源服务器；
  • 允许读、写、删除还是审批；
  • Agent 是否能再次委托给其他 Agent；
  • 高风险动作是否需要人工批准；
  • 动作如何审计、撤销和追责。

长期全局 API key 很难表达这些边界，还容易造成凭证扩散和过度授权。更合适的基线是 OAuth 2.0/OIDC + PKCE、短时 token、明确 audience/resource、RFC 9728 Protected Resource Metadata、SPIFFE/SPIRE、mTLS、细粒度 scope 和外部策略引擎。

8.2 Resource Indicators 解决什么

RFC 8707 Resource Indicators 允许客户端在授权请求或令牌请求中显式声明目标资源。授权服务器可以据此限制访问令牌的 audience，降低令牌被拿到其他资源服务器使用的风险。它对 Agent 场景非常 relevant，但不能单独解决所有多 Agent confused deputy 问题。

多 Agent 链路中，仍需要绑定用户身份、工作负载身份、资源服务器、scope、委托条件、审批记录和调用链。也就是说，resource indicator 是一个重要构件，不是完整授权系统。

8.3 Prompt injection 让数据和命令边界变成安全问题

Indirect prompt injection 中，外部内容可能被模型解释成指令。RAG 检索结果、网页、邮件、工单、issue、PR、工具返回值、长期 memory、Agent Card、工具描述以及其他 Agent 的响应，都可能携带攻击内容。

这意味着“数据”不再天然是被动数据。模型读到一段网页内容或文档片段后，可能把其中的句子当作下一步计划。可靠系统必须把不可信内容显式作为 data 处理，而不是让它自然进入指令层。

更稳妥的控制包括：工具 allowlist、读写工具分离、网络出口控制、DLP、tool-level quota、任务预算、高风险操作人工审批、policy decision、audit log、攻击回放和 red teaming。

一条不可绕过的安全原则

1模型负责理解和计划，但不能作为最终授权判断者。
2权限由策略引擎、网关、工具代理或资源服务器强制执行，即使模型输出错误请求也无法越界。
3高风险写操作必须人类审批并保留完整审计，审批 UI 要展示实际工具、完整参数、目标资源和外发目的地。

8.4 人类批准不是万能框

很多 Agent 框架在工具调用前弹一个确认框，但这并不天然安全。攻击者可能伪造工具描述，把恶意参数藏在看似正常的文本中，或通过多个低风险步骤组合成高风险结果。用户如果只看到“是否允许执行”，很难判断真实副作用。

审批界面至少应展示实际工具名、完整参数、目标资源、读写属性、代表用户、外发目的地、与原始目标关系、不可信内容引用、可回滚性和副作用范围。缺少这些信息的确认，不应被视为充分控制。

8.5 TEE 能保护什么，不能保护什么

Confidential computing 通过 TEE 和 remote attestation 保护使用中的数据，并证明运行环境。CPU TEE 和机密 VM 已较成熟，GPU confidential computing 正在演进。它可以降低宿主、运维和内存窥探风险。

但 TEE 不解决 prompt injection、越权工具调用、RAG 污染、模型错误决策、应用层授权和完整跨设备证明。采用时需要明确 TCB 范围、attestation 内容、CPU/GPU/固件/驱动版本、跨设备数据保护、调试和 profiling 限制、KV Cache 保护以及侧信道缓解。

九、可观测性与 AIOps：从普通 trace 到 Agent 状态证据

传统可观测性主要围绕请求、服务、数据库、消息队列、错误码、延迟和资源使用。AI 系统增加了模型、prompt、token、cost、embedding、retrieval、memory、tool call、approval、workflow 和 eval。观测对象从一次 RPC 扩展成一棵持续变化的 Agent 执行树。

9.1 Agent 最小观测模型

Agent run
├─ plan / workflow
├─ LLM inference：provider、model、version、prompt version、token、cost、status
├─ retrieval / embedding：source、document、chunk id、score、parameters
├─ memory read / write
└─ tool execution：tool、target resource、arguments reference、result、approval

OpenTelemetry 和 OTLP 的核心 traces、metrics、logs 管道成熟，但 GenAI semantic conventions 在 2026 年仍处于快速演进阶段。生产系统应固定 instrumentation 版本，在 Collector 层统一字段映射，避免字段重命名造成历史数据断裂。

9.2 默认不要记录完整 Prompt 和工具参数

Prompt、RAG 文本和工具参数可能包含 PII、商业秘密、金融医疗信息、凭证、内部代码或恶意注入载荷。默认记录完整内容会把观测系统变成新的敏感数据集中点。

更稳妥的方式是默认记录长度、哈希、引用 ID、脱敏摘要、token 数、模型版本和状态；确需保存原文时，放入具有独立访问控制、保留期限和审计能力的存储，trace 中仅保存引用。

9.3 AIOps 的四级权限

级别能力控制要求
L1 只读分析读取日志、指标、trace、依赖和变更记录访问控制和审计
L2 建议方案生成诊断、runbook、补丁或配置建议人工阅读、验证和选择
L3 自动操作重启、扩容、隔离异常实例等低风险可回滚动作幂等、灰度、quota、自动回滚
L4 高风险操作删除、权限变更、数据库写入、生产发布变更单、双人审批、完整审计

AIOpsLab、RCACopilot、Triangle 等研究支持 LLM 在事件收集、分诊、根因假设、多源信息汇总和受控缓解中的作用。但这些证据多来自特定组织、数据集或受控环境，不能外推出“无人值守自治数据中心已经成熟”。所有写操作仍需要 dry run、幂等键、执行计划、实际 diff、回滚方案、完成后验证和事件关联。

十、成熟度总览：哪些可用，哪些要观察，哪些别轻信

已有生产验证或强系统证据

  • InfiniBand/RDMA、RoCEv2、NCCL 基础集合通信
  • NVLink/NVSwitch、GPUDirect RDMA、rail-aligned topology
  • HTTP/JSON、SSE、JSON-RPC、gRPC、Batch API
  • Orca、vLLM、SGLang 等推理运行时机制
  • 对象存储、并行文件系统、Iceberg、Kafka/Debezium
  • OAuth/OIDC、mTLS、SPIFFE、OPA、OTLP、CPU TEE
  • Temporal 一类 durable execution

研究、早期标准或局部生产

  • UEC 完整多厂商 AI fabric 与 In-Network Collectives
  • UALink 开放 scale-up 生态
  • 跨框架统一 checkpoint 和 checkpoint-free recovery
  • CXL 内存池与 CXL pod 数据库
  • Tiga、Mako、LazyLog 等协调协议
  • 跨引擎 KV Cache 传输和会话迁移
  • GPU confidential computing
  • 多 Agent 分诊、RCA 和受控修复

炒作或证据不足

  • 一个万能 Agent 协议统一连接、事务、身份和恢复
  • 接入 MCP/A2A 就自动拥有安全层
  • LLM 可以自己可靠判断是否越权
  • SSE 重连等于任务或事务恢复
  • CDC + Kafka 端到端 exactly-once 无条件开箱即用
  • TEE 能端到端解决 Prompt injection 和工具滥用
  • 以太网或 InfiniBand 已经无条件胜出
  • 无人自治数据中心已经普遍成熟

结语：可靠的 AI 系统，是一组深度模块的组合

AI 对软件系统协议的影响，可以概括为六个变化：通信主体从独立 RPC 扩展到 collective、KV Cache 迁移和动态 Agent 消息；状态位置从数据库和缓存扩展到 GPU 显存、分离式缓存、并行文件系统和版本化索引；时间边界从毫秒请求扩展到数分钟、数小时甚至数天的长任务；信任边界从固定服务边界扩展到工具、记忆、RAG 内容和其他 Agent；协调停顿被 GPU idle 和 WAN wait 放大；治理要求必须与身份、策略、审计、provenance、成本和观测联动。

因此，2024–2026 年最可靠的路线不是等待一个“AI 时代的 TCP/IP”一统天下，而是接受协议栈的自然分层：

collective-aware fabric + KV-aware inference runtime + MCP/A2A 分层互操作 + durable execution + 外部授权审计 + GenAI observability。

好的系统不会让 Agent 在没有边界的协议空间里自由行动。它会让网络理解集合通信，让运行时管理 KV，让工作流承载恢复，让策略引擎守住权限，让可观测性记录证据，让人类最终为意图和风险负责。这不是更保守，而是 AI 系统真正能进入核心业务的前提。
