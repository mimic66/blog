副本一致性、共识选主、分布式事务：
分布式系统为什么需要它们，又如何与之共处

这三个最常被混淆的概念，其实不是三个可选方案，而是三个层次的答案： 副本一致性模型是系统对观察者做出的承诺，共识与选主决定"哪个写入算数"， 分布式事务把跨边界的业务操作拉回一致。本文从它们为什么会存在讲起， 逐一拆解各自带来的问题，以及如何验证、避免与兜底。

一、起点：单机世界里，这三个问题都不存在

理解任何分布式概念的最好方式，是先回到它们不存在的世界。在一台机器内： 一个 CPU 按程序计数器顺序执行指令，一块磁盘上的写入要么完成要么没完成， 一个内存地址在同一时刻只有一个值。顺序、原子、单一事实，这些在单机上几乎免费。

当系统跨越多台机器，三件事情同时发生，每一件都对应一个概念的诞生：

📋

数据被复制成多份

为了容灾、就近访问和读扩展，同一数据出现在多个副本上——网络延迟使它们无法瞬时同步，副本一致性模型由此产生。

💥

节点会独立地失败

机器崩溃、网络分区、进程暂停随时发生且无法及时检测，必须有一套机制决定"听谁的"——共识与选主由此产生。

🔗

业务操作跨越边界

下单要同时改订单库、扣库存、扣账户，单机事务的保护边界失效——分布式事务一致性由此产生。

二、第一层：副本数据一致性模型——系统对观察者的承诺

它为什么存在

复制数据是分布式系统最基础的动作：一份数据放在多个节点，才能在机器/机房故障时存活（容灾）、 让用户就近读取（降延迟）、用多个副本分担读压力（扩展）。 但通过网络把一个更新传播到全部副本需要时间——在"已写"和"全部可见"之间的窗口里， 不同节点就是不同的世界。一致性模型不是某种算法，而是系统对"读这个数据的人" 做出的一份关于他会看到什么的承诺。

2.1 承诺的强弱光谱

一致性模型系统的承诺代价
线性一致性操作如瞬时原子生效，任何读必看到最新写入，且保真实时间顺序最强；通常需协调/多数派，延迟与可用性代价最高
顺序一致性所有观察者看到相同的操作全序，但该序不必对齐真实时间强；牺牲实时性
因果一致性有因果关系的操作（A 发生在 B 之前）对所有人保序，并发操作可乱序中；需追踪因果
会话保证读己写、单调读（不会越读越旧）、单调写、一致前缀较低；仅在同一会话内
最终一致性停止更新后，副本最终收敛，期间允许读到旧值最低；高可用、高性能，但窗口行为不确定

Herlihy 与 Wing 1990 年对线性一致性的形式化定义是这一切的标尺： 每个操作都必须在调用与返回之间有一个原子生效点。这是最强的"单一世界幻觉"， 但要注意一个理论事实——对一般数据类型，判定一段并发历史是否线性一致是 NP-complete （Gibbons & Korach 1997），所以工程验证只能"找错"或"未发现错"，给不出"绝对无错"的证明。

2.2 三种复制架构，三种风险位置

  • 主从复制：只写 leader，再异步/同步/半同步传播到 follower。异步快但 leader 故障会丢尚未传播的写；全同步不丢但任意慢副本拖慢全体；半同步是折中。
  • 多主复制：多个节点都可写，写入就近发生——但并发写冲突需要事后解决（LWW 会静默丢数据），且必须防复制回环。
  • 无主复制（NWR）：写入 W 个副本、读 R 个副本，以 R+W>N 换取读到最新的概率；配合读修复与反熵（Gossip）收敛，但仍可能返回旧值。

2.3 会带来什么问题

🕰️

读旧值与复制延迟

写后立即读可能从尚未同步的副本读到旧值，用户看到"我的操作消失了"。

⚔️

冲突写

多主/无主下并发写同一数据，若用时间戳 LWW，慢一拍的写入被静默覆盖。

🧠

脑裂

分区使两侧各认一个主，恢复后两侧已确认的写入无法同时成立——必须有人丢数据。

Jepsen 2013 对 Redis + Sentinel 的测试至今是最好的教具：分区注入后两侧分别选主， 1998 次被确认的写入最终只有 872 次存活，已确认写丢失约 56%。 单机 Redis 本身语义很强，问题恰恰出在复制与故障切换层——这正是"模型承诺必须追到具体故障场景"的原因。

2.4 如何验证与避免

  • 按业务选承诺，而非按技术选最强：余额/库存走线性一致或读主；信息流、评论、排行榜可接受最终一致。
  • 会话级保证：写后短期强制读主、会话粘性路由到同一副本，专门消除"读己写"异常。
  • 注入故障做历史检查：在主从切换、网络分区、副本崩溃下并发读写，用线性一致性检查器（Knossos/Porcupine）或 Elle 分析收集到的操作历史。
  • 冲突显式化：用版本向量/HLC 识别并发写，业务侧解决冲突，拒绝无脑 LWW。
  • 兜底：可重建数据加短 TTL；权威数据靠周期性对账发现静默偏离。

三、第二层：共识与选主——决定"哪个写入算数"

它为什么存在

有了多副本，立刻要回答一个协调问题：两个客户端并发写同一个值，听谁的？ leader 死了，谁来接任？节点增减后，旧承诺还算不算数？ 这不是数据问题，而是"在会失败、会分区、没有全局时钟的系统里，如何让多个节点做出同一个决定"。 共识（Consensus）就是这个问题的形式化答案。

3.1 共识的三个要求，与 FLP 这盆冷水

一个共识协议必须同时满足三点：一致（所有节点决定的值相同）、 合法（决定的值必是某个节点提出的）、终止（最终一定做出决定）。

Fischer、Lynch、Paterson 1985 年证明的 FLP 不可能性给了根本性限制： 在异步网络中（消息延迟无上限），只要有一个节点可能崩溃，就不存在确定性算法 保证每次都终止。现实系统通过绕过而非推翻它来工作——引入故障检测器（超时可疑但可错）、 随机化、或租约机制，在"绝大多数时候终止"和"出错时仍安全"之间取舍。

3.2 主流机制：Paxos、Raft、Zab

  • Paxos（Lamport 1998）：共识的理论基石，通过提案编号与多数派表决保证安全；Multi-Paxos 在此之上复制状态机日志，但原文艰深、工程细节留白多。
  • Raft（Ongaro & Ousterhout 2014）：为"可理解性"设计，明确拆成选主（带随机超时的 term 选举）、日志复制、安全性三部分，是今天 etcd、Consul、TiKV 等的基础。
  • Zab：ZooKeeper 的原子广播协议，保证 leader 提议按序被多数派提交。
一个高频混淆：Gossip 不是共识。Gossip（Demers 等 1987）是概率性的反熵传播， 只能让副本最终收敛，不保证所有节点对同一决定达成一致、也没有"提交点"。 它回答的是第一层（副本传播）的问题，不是第二层。

3.3 选主会带来什么问题

🪓

脑裂

分区两侧各选出一个 leader 同时接受写入——必须靠"多数派才能提交"保证只有一侧算数。

🧟

僵尸 leader

旧 leader 没真死，只是 GC 暂停/网络阻塞；它恢复后仍以 leader 身份行动，可能覆盖新主写入。

⏳

租约与时钟

基于超时的租约若依赖各节点墙钟，时钟漂移会让"该退位的人不退"；切换窗口内的写入可能丢失。

Jepsen 2020 对 etcd 3.4.3 的测试给出精细结论：KV 与微事务确实严格可串行化， 但在"进程暂停 + 短租约 + 锁"的特定组合下，等待锁的客户端丢失租约后仍可能继续执行， 实验设置中约 18% 已确认更新丢失。根因不是 etcd 的 bug，而是分布式锁/选主的一般矛盾： 为了可用性必须在持有者疑似死亡时释放资格，但"疑似死亡"不等于真死亡。

3.4 如何验证与避免

  • 一切决定绑定 term/epoch：节点只接受当前任期的指令；旧 leader 恢复后发现 term 落后必须立刻退位并拒绝写入。
  • 用 fencing token 治僵尸：选主/锁服务发放单调递增 token，下游资源必须拒绝旧 token——这是 Kleppmann 2016 强调的关键，锁本身保护不了正确性。
  • 不依赖墙钟定生死：用逻辑任期与多数派，而非"我看超时了"；租约只用于优化，安全由 quorum 兜底。
  • 针对性故障验证：反复注入 leader 崩溃、SIGSTOP 暂停（模拟 GC）、少数派/多数派与非传递分区、数百毫秒时钟偏差、成员变更，检查是否只存在一个合法决定序列。
  • 只读请求也走校验：从 follower 读要带客户端已知的最新 index，否则可能读到旧值还以为新鲜。

四、第三层：分布式事务——把跨边界操作拉回一致

它为什么存在

前两层解决的是"一个数据"的问题。但业务上一个动作往往要同时修改多个各自独立的系统： 下单要写订单库、扣库存、扣账户、发消息。单机 ACID 的保护边界是"一个本地数据库事务"， 一旦跨进程、跨服务、跨存储，没有任何天然机制保证它们同时成功或同时失败。 网络在任意两步之间都可能中断——分布式事务就是为"跨边界的一组操作"重建一致性约束。

4.1 方案谱系：从"硬扛 ACID"到"接受中间态"

方案思路主要问题
2PC / XA 协调者先让所有参与方 prepare（持锁），全部就绪再统一 commit 同步阻塞、长持锁拖垮并发；协调者故障时参与方悬挂；早期失败后状态难恢复
TCC 业务层显式 Try 预留资源、Confirm 确认、Cancel 释放 隔离与性能好，但每个资源都要实现三接口，侵入性极强，设计成本高
Saga 拆成一串可独立提交的本地事务，某步失败则执行对应补偿（Garcia-Molina & Salem 1987） 补偿不是回滚：副作用已被观察、无全局锁、中间态可见；需防空补偿、悬挂、超时与重复补偿
本地消息表 / 事务消息 业务数据与待发消息同一本地事务提交，异步保证投递 最终一致；消费端必须幂等，需处理堆积、重复、乱序

4.2 最需要被理解的一点：补偿 ≠ 回滚

数据库回滚是"当作什么都没发生"。Saga 补偿做不到：已经发出的券可能已被使用、 已发的短信/邮件无法撤回、已经扣过的款要靠一笔新的退款交易拉回。 补偿产生的是新业务事实，不是对旧事实的擦除。 因此设计 Saga 必须回答：中间状态用户可见吗？补偿失败谁重试？外部依赖长期不可用怎么办？ ——回避这些问题，"最终一致"就会退化成"永久不一致 + 客服背锅"。

4.3 会带来什么问题

  • 超时语义被误读：超时只代表"调用方没在时限内拿到结果"，不代表操作没执行；直接重发就产生两笔扣款/两笔提币——这是资金事故最常见的根因。
  • 幂等缺失：消息重复投递、回调重复、人工重试在没有业务唯一键时全部变成真实重复操作。
  • 补偿三重陷阱：空补偿（对从未成功的 Try 执行 Cancel）、悬挂（Cancel 先于 Try 到达后资源被锁死）、补偿重复执行。
  • 中间态可见：Saga 进行中用户可能看到"已扣款但无订单"，需要业务上可解释、状态可查询。

真实事故中，BitMEX 2023 年重复提币复盘是最完整的样本：一次 Tron 网络提币在 "链上交易状态解释、HTTP 响应码解释、托管方 API 消息不一致、人工重提流程被错误启用" 的组合失效下产生第二笔交易，形成 5 万 USDT 链上缺口； 最终是交易引擎的实时自审计（对账）触发停机止损。这正是三层问题叠加的典型形态。

4.4 如何验证与避免

  • 先在业务上"去分布式事务化"：同一业务尽量收敛到单库单 key（如用户维度分库后该用户的全部操作落同一库），能用本地事务解决就不跨边界——最好的分布式事务是不需要它。
  • 双写走 Outbox：业务数据与待发事件在同一本地事务写入发件箱，由 CDC（如 Debezium）至少一次投递，消费端幂等——不要用"先更新库再发 MQ"。
  • 全写操作幂等：稳定业务幂等键 + 数据库唯一约束占单（不是先查后插）；超时只查原单、禁止新建交易。
  • 状态机单向迁移：把订单/支付/库存的合法转移写死，非法跳转直接拒绝；补偿本身幂等。
  • 逐步崩溃验证：用 Testcontainers 真实中间件，在事务的每一步注入崩溃/超时/重复，断言最终状态；Saga 额外验证空补偿、悬挂与补偿重试。
  • 对账兜底：订单、流水、分录、渠道/链上记录周期核对，差错冻结后用补偿流水修正，禁止手工改数。

五、问题发生时，系统"长什么样"：可观察的故障表现

一致性缺陷最难缠的地方在于：系统通常不报错、不崩溃、还返回成功， 错误以"数据看起来不对"的方式悄悄出现。运维和客服最先感知到的往往是"幽灵现象"—— 刷新一下又正常了、两个页面数字对不上、用户坚称操作成功但系统查无记录。 把这些表现与具体的层对应起来，是缩短定位时间的关键。

5.1 副本一致性（L1）出问题时

核心特征：同一个数据，不同入口看到不同的值；矛盾随时间"自愈"。

  • "操作消失术"：用户刚提交评论/改完资料，页面刷新后内容不见了，过几分钟又出现——读到了尚未同步的旧副本（读己写异常）。
  • "越刷新越旧"：第一次看到新数据，再刷新反而退回旧版本——连续请求被负载均衡打到了复制进度不同的副本（违反单调读）。
  • "页面精神分裂"：列表页显示已付款，点进详情页显示待支付；同一页面的两个组件数字互相矛盾——它们读了不同副本。
  • "我的更新被别人吃了"：两人同时编辑，后保存的人覆盖了先保存的内容且无任何冲突提示——多主 LWW 静默丢写。
  • 主从切换后的"集体失忆"：故障切换完成后，一批故障前已提示"成功"的写入永久消失，且不会随时间恢复——异步复制中未传播的写随旧主下台而丢失（Redis Jepsen 场景）。
  • 监控特征：各副本间复制延迟（replica lag）拉大；同一 key 跨节点查询结果不一致；错误率无明显升高但用户投诉上升。
判别口诀："矛盾 + 会自愈 + 换个入口结果不同" → 大概率 L1。 这类问题重启/重登/等待常常"看起来修好了"，但数据偏离可能已经落库，不能因现象消失就关单。

5.2 共识 / 选主（L2）出问题时

核心特征：出现两个"权威"同时发号施令，或系统在"谁负责"上反复横跳。

  • "两个老板同时在"：监控里短暂出现两个 leader，两侧都在接受写入——脑裂；恢复后必有一侧的确认写被丢弃。
  • "死而复生的主"：旧 leader 经历一次长时间 GC 暂停或网络阻塞后"醒来"，不知道自己已被罢免，继续处理请求并覆盖新主的决定——僵尸 leader。
  • "无限重选"：日志里 term/epoch 数字飞速递增、leader 频繁切换，系统持续不可用——节点时钟漂移或心跳超时设置过短，无法形成稳定多数派。
  • "持锁者失效"：客户端以为自己持有分布式锁在执行，锁其实已因租约到期授予他人，两个客户端同时操作同一资源（如同时执行同一定时任务、重复发货）。
  • "多数派一倒全瘫"：少数节点故障不影响服务，但一旦过半节点不可达，整个集群拒绝读写且不会自动降级——这是共识系统正确的代价，但常被误报为"bug"。
  • 监控特征：term 跳变、leader 选举事件密集；租约过期告警；分区两侧各自有写入计数；客户端偶发 "not leader" / term 过期错误。
危险信号：L2 问题不像 L1 那样会自愈——脑裂期间两侧的写入冲突必须有人丢数据。 一旦怀疑双主，应立即停止对受影响分区的写入、保留两侧日志，而不是等它们"自己合并"。

5.3 分布式事务（L3）出问题时

核心特征：钱、库存、状态对不上；操作被执行了"两次"或"半步"。

  • "幽灵重复扣款"：用户只点了一次支付，银行/账单里却有两笔——超时后客户端或人工重试，而服务端没有幂等键占单。
  • "扣款成功、订单不存在"：账户余额少了，订单列表却查无此单，状态长时间停在"处理中"——Saga 某步失败后补偿未触发或补偿失败，中间态永久悬挂。
  • "库存负数 / 超卖"：同一批库存被多个并发请求扣成负值——跨服务操作缺少预留/条件更新，或 TCC Try 未生效。
  • "退款退了两次" / "券用了又回来"：补偿动作本身被重试执行，或空补偿、悬挂导致资源状态错乱。
  • "消息石沉大海"或"轰炸式重复"：下游迟迟收不到事件（消息表轮询挂起），或恢复后同一事件被投递多次，无幂等的消费方产生重复业务。
  • "永远处理中"：大量订单卡在中间状态，只能靠人工 SQL 改状态——说明状态机没有非法转移保护，也没有超时收敛机制。
  • 监控特征：对账差异（借贷不平、订单与流水不符）；补偿队列积压与重试次数异常；渠道/链上记录与本地台账偏离。

5.4 三层故障表现速查表

观察角度L1 副本一致性L2 共识选主L3 分布式事务

还有一类最棘手的情况：三层叠加失效。BitMEX 2023 事故中， 用户先看到提币"处理中"长时间不结束（L3 超时），人工重提后实际链上已执行两笔（L3 幂等缺失）， 最终靠交易引擎实时自审计发现账实偏离才止损。当现象同时符合多行特征时， 应假设是组合问题并从最底层开始排查——上层的"异常"常常只是下层偏离的回声。

六、三层如何咬合：辨析表与失效症状

概念混淆是错误选型的直接来源，下表列出最常见的几组误读：

常见说法实际情况所属层
"我们用 Gossip 做共识"Gossip 只做概率性副本收敛，无一致决定点L1，非 L2
"多副本 = 有事务保证"副本只解决一份数据的可用性，不管跨系统操作L1 ≠ L3
"存储有 Raft，业务就有 ACID"Raft 只在存储内部保证日志一致，不跨服务L2 ≠ L3
"Kafka 事务 = 端到端 exactly once"KIP-98 只覆盖 Kafka 内部 read-process-write边界在存储内
"主从复制就是共识算法"普通异步主从复制无多数派表决，故障窗口可能丢确认写L1，非 L2
"Saga 回滚了"Saga 只有补偿（新事实），没有数据库意义的回滚L3

反向定位（看到现象判断哪一层失败）的详细表现已在上一节展开，可对照第 5.4 节速查表。

七、工程纪律：验证手段与检查清单

三层的验证方法共享同一套工程工具箱，按介入阶段排列：

阶段手段主要回答
设计期TLA+/PlusCal 形式化建模协议在有限模型内是否存在反例（脑裂/丢写/死锁）
开发期状态机表 + 属性测试（不变量）任意操作序列下资金守恒、无非法跳转、无超卖
集成期Testcontainers 真实版本 + 契约测试真实驱动与中间件行为、接口兼容
故障期Jepsen / Toxiproxy / 混沌注入分区、崩溃、暂停、时钟偏差下历史是否仍合法
生产期可观测性 + 实时对账 + 备份恢复演练静默偏离能否被及时发现并补偿

分布式一致性设计评审清单

  1. 分层：需求落在哪一层——是副本承诺（L1）、协调决定（L2）、还是跨系统事务（L3）？有没有用错工具？
  2. L1：该数据业务上需要什么承诺？读己写异常是否用会话路由消除？冲突是否显式解决而非 LWW？
  3. L2：是否只认多数派与当前 term？旧主回归能否被识别？保护正确性的锁是否带 fencing token？
  4. L3：能否在业务上单库收敛？不能时是否选了与代价匹配的方案（2PC/TCC/Saga/消息表）？
  5. L3：补偿的空执行/悬挂/重复是否处理？超时是否只查不重？全写接口是否幂等？
  6. 验证：是否在每一步崩溃、分区、暂停下做过实验，而不只是正常路径？
  7. 兜底：对账是否覆盖业务/渠道/链上？差错是否走补偿流水？备份是否真的恢复过？

八、结语：与不完美的保证共处

没有全局正确，只有分层承诺与收敛回路

三个概念存在的根源始终是同一个物理事实：网络会延迟与中断、节点会独立失败、 系统里没有全局时钟。我们无法消灭这些约束，只能在每个层次上做出明确的承诺并为承诺的失效准备后路。

副本模型说"你会看到什么"，共识选主说"听谁的"，分布式事务说"跨出去的一步如何收回来"。

最可靠的系统并不是用了最强算法的系统，而是承诺与业务匹配、每层边界清晰、 且在每一个可能分叉的地方都预设了收敛回路的系统。 GitHub 2018（跨区复制不一致）、GitLab 2017（备份不可恢复）、BitMEX 2023（三层组合失效） 共同说明：出问题的团队往往不是不懂算法，而是把某一层的保证错放到了另一层。

作为工程师，接受"没有绝对一致的证明"并不是悲观，而是成熟—— 它让我们把精力从"寻找银弹"转向诚实的分层、激进的验证、和可靠的兜底。 这正是分布式系统设计中最核心、也最不可替代的判断力。
