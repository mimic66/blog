请求驱动、任务驱动、数据驱动

同样是分布式系统，"主要被什么驱动"决定了它的时间尺度、一致性诉求、耦合方式、失败可见性与容量模型。看清楚自己在做的是哪一类，设计取舍和质量保障才不会用错药方。
2026-11-04 · 分布式架构与质量保障 · 约 43 分钟阅读 · 写给要为不同形态系统做设计与测试的工程师与 QA

一个常见的误区是：团队学了一套"分布式最佳实践"，然后不加区分地套用到所有系统上。但你只要对比三类系统，就会发现它们关心的问题几乎没有交集：

  • 用户点"立即支付"，系统必须在几百毫秒内返回成败——这是请求驱动；
  • 下单后要通知仓库、扣积分、发券，这些不必让用户等，扔进队列后台慢慢做——这是任务驱动；
  • 每天要把数十亿条行为日志聚合成报表、训练特征、实时大盘——这是数据驱动。

用请求驱动的思路做数据管道，会被海量数据淹没；用数据管道的思路做支付，会让用户等到崩溃。架构没有银弹，只有与驱动力匹配的取舍。本文先定义三者并横向对比，再分别讲设计要点和差异化质量保障，最后用真实事故印证。

一、先分清：三种"驱动力"到底是什么

这里的"驱动力"指系统前进的主要触发方式和时间约束——它决定了"谁在等、等多久、等不到会怎样"。

请求驱动 Request-Driven

由外部请求实时触发，调用方同步阻塞等待结果。

  • 典型：Web/API、RPC、在线交易
  • 时间尺度：毫秒~秒
  • 用户就在链路另一端等
  • 核心矛盾：延迟、可用性、扇出

任务驱动 Task-Driven

由异步任务/消息触发，生产者不等结果，消费者稍后处理。

  • 典型：消息队列、后台任务、Saga、工作流
  • 时间尺度：秒~分钟~小时
  • 时间解耦，可削峰、可重试
  • 核心矛盾：不丢、不重、有序、积压

数据驱动 Data-Driven

由数据本身的到达/批量触发，目标是把数据变换成结果。

  • 典型：流处理、批处理、ETL、数仓
  • 时间尺度：分钟~天
  • 关注吞吐、正确性、可重算
  • 核心矛盾：结果对不对、全不全、静默错误

1.1 一个关键澄清："事件驱动"不是第四类，它横跨后两类

很多人会问：那"事件驱动（event-driven）"算什么？Martin Fowler 在 2017 年专门写过《What do you mean by "Event-Driven"?》，指出这个词至少有三种含义，它们分别落在不同的驱动力上：

Fowler 的三种事件模式含义更接近哪类驱动力
事件通知 Event Notification发个事件"订单已创建"，接收方自己决定后续，常需回查源数据任务驱动（异步触发动作）
事件携带状态转移 Event-Carried State Transfer事件里直接带上所需状态，接收方无需回查介于任务与数据之间
事件溯源 Event Sourcing把事件作为唯一事实来源，状态由折叠事件得出，常配 CQRS数据驱动（事件即数据）

[L2] martinfowler.com/articles/201701-event-driven.html。所以本文不把事件驱动单列，而是按其语义归位：异步通知当任务系统保障，事件溯源/CQRS 当数据系统保障。

判定你面对的是哪类系统，只需问三个问题：①谁在等结果（用户在线等 / 没人当下等 / 下游等一批结果）？②可接受的延迟是多少（毫秒 / 秒分钟 / 分钟天）？③结果错了谁最先发现（用户立刻报错 / 稍后对账发现 / 可能永远没人发现）？第三个问题尤其重要——它直接决定了质量保障的难度层级。

三、请求驱动系统：设计要考虑什么

3.1 同步链路的可用性是"相乘"的

请求驱动最残酷的数学是：一个请求要串联经过 N 个服务，整体可用性约等于各服务可用性之积。即使每个服务都有 99.9% 的可用性，串联 5 个就降到约 99.5%，串联更多则加速恶化。再叠加 Jeff Dean《The Tail at Scale》（CACM 2013）指出的长尾效应：单组件随机请求可低至 10ms，p99 却能到 140ms；一个请求扇出到数百个下游时，整体延迟由最慢的尾部决定，而不是平均值。

请求驱动设计必须正面回答的问题

  • 超时：每个出站调用都设超时，且全链路超时要逐层收敛（下游超时 < 上游），避免线程被无限占满；
  • 重试要克制：只对幂等读操作快速重试，用 retry budget 限制总量——无限重试是级联风暴的头号引信；
  • 熔断与降级：下游持续故障时快速失败，提供兜底（缓存/默认值/弱化功能），保住核心链路；
  • 舱壁隔离：线程池/连接池按依赖隔离，防止一个慢下游拖垮整个进程；
  • 尾延迟治理：对冲请求（hedged requests，假设操作幂等）、"足够好即返回"；
  • 过载保护：限流、排队、负载 shed，在系统承压时主动丢弃超出能力的请求而不是被压垮；
  • 同步调用链尽量短：能异步化的非关键路径（通知、积分）移出用户链路，每个用户请求的同步扇出要有上限。
设计心法：请求驱动系统是在"和时间与概率搏斗"。默认假设每个下游都会慢、会挂、会超时，然后把这些失败都设计成系统能优雅承受的常态——而不是寄望于"网络可靠、下游都健康"这两个被分布式谬误反复证伪的前提。

四、任务驱动系统：设计要考虑什么

4.1 先认清现实：主流消息系统默认都是 at-least-once

任务驱动设计的起点，是接受一个被官方文档反复确认的事实：Amazon SQS 标准队列、Google Pub/Sub 默认都是至少一次投递——消息可能被投递多次，即使已 ack 也可能再投。SQS 要顺序/去重需另用 FIFO 队列（有吞吐上限），Pub/Sub 的 exactly-once 也是受限特性。因此，"消费者必须幂等"不是可选项，是任务驱动系统的地基。

幂等的实现手段（按场景选用）

幂等键 + 去重表（如 Stripe Idempotency-Key，服务保存首次结果，重放同 key 直接返回）；数据库唯一约束兜底；乐观锁版本号；状态机防重（只允许合法的状态转移，重复消息到达时发现"已处理"直接跳过）；业务唯一 ID 做天然去重键。[L1] docs.stripe.com/api/idempotent_requests

4.2 Kafka 的 exactly-once：能力真实，但边界必须讲清

Kafka 自 0.11（2017，KIP-98）引入幂等 producer（PID + 序列号，保证单分区、单 producer 会话内不重复）与事务（让"读偏移→更新状态→写多分区"原子提交，read-process-write）。Confluent 官方同时明确限定：EOS 只覆盖 Kafka 边界内的 read-process-write；若处理中发了 RPC 更新外部数据库、或用自定义 client 读写 Kafka，这些外部副作用不被保证恰好一次。

"You Cannot Have Exactly-Once Delivery"——Tyler Treat（2015）从两将军问题与任意故障不可判定的角度论证：在不可靠网络下，端到端"恰好一次"无法仅靠投递本身保证，最终仍要落到幂等/去重。 —— 这与 Kafka EOS 并不矛盾：后者把"恰好一次"严格限定在受控管道内，外部副作用仍需幂等。注意作者是 Tyler Treat，常被误作 Kleppmann。

任务驱动设计必须正面回答的问题

  • 投递语义：明确选 at-most-once / at-least-once / exactly-once，并按"at-least-once + 消费端幂等"做默认设计；
  • 顺序：Kafka 只保证分区内有序，需要端到端顺序就用业务键路由到固定分区，并评估 rebalance 期间的影响；
  • 消费进度：先处理再提交偏移（至少一次），避免"先提交后处理"导致丢消息；
  • 失败隔离：反复失败的毒消息（poison message）转入死信队列，不能让一条坏消息卡死整批（注意 Lambda+SQS 的整批重投行为）；
  • 重试分层：快速重试吸收瞬时故障，长周期慢重试承载持续故障，避免立即无限重试压垮下游；
  • 背压与扩缩容：消费者组按积压扩缩，处理速度要能跟上生产速度，遵循 Reactive Streams 的非阻塞背压；
  • 分布式事务：跨服务长流程用 Saga——编排式（中央协调器，流程清晰）或协作式（事件驱动，去中心化）二选一，并为每步配补偿；
  • 双写问题："写库 + 发事件"用 Transactional Outbox 合成一个本地事务，由 relay 投递，避免二者不一致；
  • 可追踪：业务关联 ID 全链路透传，任务有显式状态机，否则异步流程出了问题无从排查。

4.3 调度类任务的特殊坑

定时/工作流系统还要额外处理"漏触发"与"重复触发"：Quartz 有 misfire 概念（到点未触发，需配置补跑或跳过）；Airflow 的 catchup/backfill 会为历史所有未跑区间补跑、瞬间放大负载（默认值随版本变化，须按版本核实）；Temporal 的 durable execution 让故障后从最后完成的步骤恢复，但 Activity 默认 at-least-once 重试，副作用仍须幂等。

设计心法：任务驱动系统是在"和不确定性共处"。你换来的是时间解耦、削峰填谷和可重试，但账单是重复、乱序、积压与最终一致。把幂等做扎实、把失败隔离到 DLQ、把积压当成一等可观测指标，这套架构才真正稳。

五、数据驱动系统：设计要考虑什么

5.1 批与流：Lambda 与 Kappa 的取舍

数据驱动系统首先要决定批流形态。

  • Lambda 架构（Nathan Marz，2011/2015）：批处理层（全量重算、结果完整准确）+ 速度层（实时、近似）+ 服务层合并。优点是兼顾准确与时效，缺点是要维护两套处理逻辑；
  • Kappa 架构（Jay Kreps 2014）：用同一套可重放的流处理逻辑兼顾实时与重算，质疑 Lambda 双链路的维护成本。前提是有可长期保留、可重放的日志（如 Kafka）。

5.2 流处理正确性：event time、watermark 与窗口

Google Dataflow Model（Akidau 等，PVLDB 2015）奠定了无界乱序数据处理的核心概念：event time（事件发生时间）vs processing time（被处理时间）、窗口（滚动/滑动/会话）、watermark 和触发器。关键认知是：watermark 是启发式进度估计——可能过晚（迟迟不产出结果）或过早（窗口关闭后迟到的数据无处安放）。

默认配置会悄悄丢数据。Apache Flink 文档明确：event-time 窗口在 watermark 越过窗口结束后触发并清理，此后到达的记录默认视为迟到并丢弃（allowedLateness 默认 0）。必须显式配置 allowed lateness + 侧输出收集迟到事件，并评估 watermark 过早的丢数风险——"默认不丢"是错觉。

5.3 端到端 exactly-once 的真实条件

Flink 的端到端恰好一次靠三个条件拼起来：source 可重放（offset）+ checkpoint 用 barrier 对齐（异步屏障快照，Carbone 等 2015）+ sink 支持事务/两阶段提交。这意味着对不支持事务的外部系统、或幂等不成立的副作用，端到端 EOS 无法保证；而 barrier 对齐在严重反压下还会引入额外延迟。

数据驱动设计必须正面回答的问题

  • 可重跑 / 幂等写入：任务失败重跑不能产生双写——用 upsert/merge、分区覆盖、幂等 sink，保证"任意重算结果不变"；
  • 回填：backfill 必须可控、限速、可分批，避免重算历史把在线集群打满；
  • 迟到与乱序：显式定义 watermark 策略、allowedLateness、迟到数据侧输出，不接受默认丢弃；
  • Schema 演进：用 Avro/Schema Registry 管理兼容（BACKWARD/FORWARD/FULL），新增字段带默认值——但要明白结构兼容不等于语义兼容（改名、换单位会通过检查却改变含义）；
  • 数据同步：CDC（如 Debezium）依赖源库日志保留，位点丢失会断档；全量+增量要能对齐；
  • 数据血缘：记录每个结果由哪些上游、哪段逻辑产生，否则静默错误无法追溯；
  • 空结果/异常结果告警：数据管道"不报错"不代表"结果正确"，要对输出的量、分布、空值率做监控；
  • 资源倾斜：按 key 分布评估数据倾斜，个别热点 key 可拖垮整个算子。

数据质量的六个经典维度

学术依据可追溯到 Wang & Strong（1996）与 Strong/Lee/Wang（CACM 1997）对数据质量的体系化：准确性、完整性、一致性、及时性、唯一性、有效性。数据驱动系统的质量保障，本质就是对这六维做持续度量与对账，而不只是保证"任务跑成功了"。[L1] Wang & Strong, JMIS 1996；Strong/Lee/Wang, CACM 1997

设计心法：数据驱动系统最大的敌人是"静默失败"——系统运行正常、没有报错，但输出的结果是错的、缺的、重复的，而且可能很久都没人知道。因此设计的核心不是"让任务跑完"，而是"让任何错误结果都能被及时发现并可无损重算"。

六、混合架构：真实系统从来不是单一驱动力

现实中的大型系统几乎都是三者交织，关键是在正确的环节用正确的驱动力。以一次电商下单为例：

七、质量保障：三类系统的差异化打法

这是本文的落脚点。同一套测试团队，面对三类系统必须切换质量模型。

7.1 请求驱动：围绕"用户当下的体验"保障

  • 超时与故障注入测试：主动注入下游延迟/错误，验证超时生效、熔断打开、降级兜底正确、核心链路不塌；
  • 性能与尾压：不只看平均延迟，重点压 p99/p99.9；做过载与限流验证；
  • 级联故障演练：验证单个下游故障不会沿链扩散、重试不会形成风暴；
  • 可用性串联核对：审视同步扇出深度，推动非关键路径异步化；
  • 强弱依赖梳理：明确哪些下游挂了必须报错、哪些可降级，并逐一对其注入故障验证。

7.2 任务驱动：围绕"消息的不丢不重不积压"保障

  • 幂等专项测试：重复投递同一条消息，验证只生效一次——这是任务系统的头号用例；
  • 消息丢失验证：模拟消费者中途崩溃，验证"先处理后提交"下消息不丢；
  • 顺序测试：在要求有序的链路上验证分区路由与 rebalance 期间的顺序；
  • 毒消息与 DLQ：构造反复失败的消息，验证其进入 DLQ 且不阻塞其他消息，并对 DLQ 建监控告警（DLQ 只隔离、不会自己被看见）；
  • 积压与恢复演练：制造大量积压，验证消费组能扩缩追上、lag 可观测、追上后结果正确；
  • Saga 补偿测试：在任意步骤注入失败，验证补偿链完整、无悬挂状态、补偿本身也幂等；
  • Outbox 一致性：验证库与事件最终一致、relay 重复投递被幂等消费；
  • 调度任务：验证漏触发（misfire）与重复触发下行为正确，backfill 不冲垮系统。

7.3 数据驱动：围绕"结果的正确与可重算"保障

  • 数据对账（reconciliation）：源端与目标端按条数、金额、关键指标双向核对，这是发现静默错误的核心手段；
  • 完整性校验：验证无遗漏（总量、分区量、边界）、无重复（唯一性）、空值率与分布合理；
  • 可重跑验证：同一批数据重复跑，结果必须一致、无双写；
  • 迟到/乱序测试：注入晚到与乱序数据，验证 watermark、allowedLateness、侧输出行为符合预期、不静默丢弃；
  • Schema 兼容测试：验证新旧 schema 消费与回放的兼容性，并关注结构通过但语义改变的风险；
  • CDC 一致性：验证全量+增量对齐、日志保留期内不断档；
  • 异常结果监控：对输出量骤降/骤增、空结果、分布漂移设告警——因为数据系统出错常常"绿灯常亮"；
  • 数据质量规则化：把六维（准确/完整/一致/及时/唯一/有效）落成可自动执行的校验与阻断，而非人工抽查。
三类质量保障的根本区别：请求驱动测的是"此刻快不快、挂没挂"，失败会立刻被用户看见；任务驱动测的是"异步动作最终对不对、有没有丢重"，失败要靠积压和对账暴露；数据驱动测的是"一批结果准不准、错了能不能发现和重算"，最大的恐惧是系统不报错、却静默地给出错误答案。越往右，越不能依赖"系统会告诉我出错了"，越要主动建立独立于系统自身的核对手段。

八、真实事故印证：不同驱动力，踩不同的坑

8.1 请求驱动：同步依赖 + 重试风暴如何放大故障

AWS DynamoDB us-east-1（2015-09-20）官方 postmortem

一次短暂网络抖动后，大量存储服务器同时向 metadata 服务请求 membership；因 GSI 使 membership 体积翻倍、metadata 容量不足，响应超时，存储服务器自我摘除，请求重试进一步压垮 metadata——一次局部抖动在同步依赖与重试放大下演变为区域级故障。改进：提升 metadata 容量、增加 membership 规模监控。aws.amazon.com/message/5467D2

AWS S3 us-east-1（2017-02-28）官方 postmortem

值班工程师按既有流程执行服务器下线命令时，"one of the inputs to the command was entered incorrectly"（官方措辞，即坊间所称"typo"，原文未用该词），下线了远超预期的服务器，波及 index 与 placement 子系统，核心中断约 4 小时余；S3 不可用又连带 EC2 启动、EBS 快照、Lambda。改进：工具限速下线、最低容量保护、加速 cell 化。aws.amazon.com/message/41926

8.2 任务/数据驱动：队列、积压与部署一致性

AWS Kinesis us-east-1（2020-11-25）官方 postmortem

前端扩容使每台服务器线程数超过 OS 配置上限，shard-map 缓存构建失败、前端无法路由，只能以每小时数百台的慢速重启数千台前端，告警起约 17 小时；Kinesis 积压又连带 Cognito 等服务。这是典型的"容量变更 + 积压"型故障。aws.amazon.com/message/11201

PagerDuty Kafka（2025-08-28）官方工程复盘

Kafka 消息系统故障级联到美国区域，通知、webhook、REST API 降级；恢复阶段出现通知延迟与重复 webhook——重复 webhook 恰好印证了 at-least-once 下"消费端必须幂等"的铁律。pagerduty.com/eng/august-28-kafka-outages

Knight Capital SMARS（2012-08-01）SEC 一手处罚令

部署新订单路由代码时，8 台服务器中有 1 台没拷贝到新代码，旧的已停用死代码被可复用的标志位激活，约 45 分钟内向市场发出数百万笔错误订单，在 154 只股票成交超 3.97 亿股。实际亏损为 4.6 亿美元（$460M）——流传的 4.4 亿系误传，以 SEC（Release No. 34-70694）为准。根因是无第二人复核、无书面部署审查。sec.gov/litigation/admin/2013/34-70694.pdf

8.3 数据驱动：备份全失效与静默损坏

GitLab.com 数据库（2017-01-31）官方 postmortem

高负载下复制延迟，secondary 因 primary 已清理 WAL 且未做归档而复制中断；工程师试图在 secondary 清空数据目录重建时误在 primary 执行，约 300GB 数据仅剩约 4.5GB。更致命的是多层备份在需要时全部失效（pg_dump 版本不匹配静默失败、快照未启用），最终靠约 6 小时前的手动 LVM 快照恢复。它同时警示："备份存在"不等于"备份可恢复"，恢复演练是刚需。about.gitlab.com/blog/2017/02/10/postmortem

Meta 静默数据损坏（2021）官方工程博客

CPU 静默错误可在压缩/解压等环节产生未被察觉的数据损坏，并沿栈传播导致数据库"丢行"，在数十万台机器规模下可能数月才被发现——这正是数据驱动系统最深的恐惧：系统没有任何报错，数据却已经坏了。结论是仅靠硬件冗余不够，还需容错软件架构与生产级主动检测。engineering.fb.com/2021/02/23/data-infrastructure/silent-data-corruption

证据说明：以上时间、影响与根因均以官方 postmortem / SEC 原文为准；个别细节（如 GitLab 精确停服时长为二手汇编）不应在引用时坐实。

结语：先认清驱动力，再谈架构与质量

回头看，三类系统没有高下，只有"是否匹配它要解决的问题"：

  • 请求驱动为"人在等"而设计，和时间与概率搏斗，质量靠超时、熔断、降级与尾压保障；
  • 任务驱动为"不必等、可延后"而设计，和不确定性共处，质量靠幂等、DLQ、积压监控与补偿保障；
  • 数据驱动为"结果必须正确"而设计，和静默失败搏斗，质量靠对账、完整性、可重算与数据质量规则保障。

对工程师，最重要的能力是在设计之初就诚实回答："我这个系统到底被什么驱动？谁在等？错了谁会发现？"对 QA，最重要的能力是切换质量模型——而不是用同一套"功能点 + 边界值"打天下。

越往异步和数据的方向走，失败越不会主动现身。因此成熟团队会为请求系统练"快速降级"，为任务系统练"不丢不重"，为数据系统练"独立对账与无损重算"。看清驱动力，架构才不会用错药方，质量才能真正打在系统最脆弱的地方。
