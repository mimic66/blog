架构启示：LLM 应用如何设计多模型容灾？

2026-09-07 · 阅读约 10 分钟 · 标签： 最佳实践 架构设计

这次集体故障给所有依赖大模型的应用敲响了警钟：单一模型服务商是不可靠的。本文从架构角度，探讨如何设计具备高可用性的多模型系统。

一、核心原则：模型抽象层

一切的基础是：不要让业务代码直接依赖某一家的 SDK。

在业务逻辑和模型 API 之间增加一个抽象层，将模型调用统一成内部标准接口。这样切换底层模型时，业务代码不需要任何改动。

抽象层应该统一什么？

  • 请求格式：统一的消息格式（role / content 结构）
  • 响应格式：统一的返回结构（text、usage、finish_reason 等）
  • 流式输出：统一的 SSE / 流式接口
  • Tool Calling：统一的函数调用格式
  • Embedding：统一的向量输出接口
推荐方案 如果不想自己造轮子，可以使用开源的 LLM 网关，如 LiteLLM、Portkey、OneAPI 等，它们已经封装了几十家模型的 API。

二、故障转移策略

光有抽象层还不够，还需要自动的故障转移机制。

策略 1：简单重试 + 切换

最基础的方案：主模型调用失败后，自动重试 1-2 次，如果还是失败，切换到备用模型。

  • 优点：实现简单，改动小
  • 缺点：故障检测慢（每次都要等超时），用户体验差
  • 适合：对可用性要求不高的内部工具

策略 2：健康检查 + 主动切换

在后台持续探测各模型服务的健康状态（定时发送心跳请求），维护一个"可用模型列表"。实时流量只走健康的模型。

  • 优点：故障发现快，用户几乎无感知
  • 缺点：需要额外的健康检查机制，增加复杂度
  • 适合：面向用户的生产应用

策略 3：流量分发 + 多活

把流量同时分发给多个模型服务商，任何一个出问题，流量自动切到其他健康的实例上。

  • 优点：可用性最高，单个服务商故障几乎不影响整体
  • 缺点：成本高（需要维护多套接入），需要处理模型差异
  • 适合：对可用性要求极高的核心业务

三、降级方案设计

当所有大模型都不可用时（就像这次集体故障），你的应用应该怎么表现？直接报错吗？

更好的做法是设计多层降级方案：

降级层级

级别 方案 用户体验 适用场景
L1 正常 主力模型 + 备用模型自动切换 几乎无感知 单一服务商故障
L2 降级 切换到更小/更慢的模型 质量略降，但功能可用 主流模型都故障
L3 兜底 使用本地小模型 / 缓存 / 模板 功能受限，但基础可用 所有云端 API 不可用
L4 熔断 关闭 AI 功能，提示用户稍后重试 功能不可用，但不崩溃 完全不可用，防止雪崩

本地兜底模型

在服务器上跑一个轻量级开源模型（比如 Qwen-7B、Llama-3-8B 级别），作为极端情况下的兜底。虽然效果不如大模型，但至少能处理简单请求。

  • 7B 模型在一张消费级 GPU 上就能跑
  • 甚至在 CPU 上也能跑（速度慢一些）
  • 对于简单的分类、摘要、问答场景，小模型也够用

四、缓存策略

减少对模型 API 实时依赖的最有效手段之一就是缓存。

可以缓存的场景

  • 语义缓存：相似的问题直接返回缓存答案（用 Embedding 相似度匹配）
  • 确定性任务：代码生成、翻译等任务，相同输入可以直接复用结果
  • 高频查询：知识库问答、常见问题解答等，命中率很高

一个好的缓存系统可以减少 30%-70% 的模型调用，既省钱又提高了系统的抗故障能力。

五、超时、重试与熔断

合理的超时设置

不要设置过长的超时时间。大模型 API 正常响应通常在几秒内，如果超过 30 秒还没返回，大概率是出问题了。

  • 简单问答：10-15 秒超时
  • 复杂推理 / 长文本：30-60 秒超时
  • 流式输出：首 token 超时 5-10 秒

重试策略

  • 指数退避重试：失败后等待时间逐渐加长（1s → 2s → 4s）
  • 限制最大重试次数：通常 2-3 次就够了
  • 只对幂等请求重试：创建类操作要谨慎，避免重复执行

熔断器模式

当某个模型的错误率超过阈值（比如 50%）时，自动"熔断"——暂时不向它发请求，等它恢复了再慢慢切回去。

这可以避免在故障期间继续发送大量请求，既减少了用户等待的时间，也给了故障服务恢复的喘息空间。

六、监控与可观测性

你没法管理你没法度量的东西。LLM 应用的监控至少要覆盖：

  • 可用性：各模型的成功率、错误率
  • 延迟：p50、p95、p99 延迟，首 token 延迟
  • 成本：token 消耗、费用统计
  • 质量：输出质量评分、用户反馈

建议接入专门的 LLM 可观测性平台，或者自己搭建基础的监控仪表盘。这次故障中，很多团队是用户报告了才知道服务挂了，这就是监控缺失的表现。

七、参考架构图

推荐的生产级 LLM 应用架构

用户请求 → 负载均衡 → LLM 网关（抽象层 + 故障转移 + 缓存） → 多模型服务商（主 + 备 + 本地兜底）

配套：健康检查、监控告警、熔断降级、用量统计

八、成本与收益的平衡

当然，容灾是有成本的。接入多家模型、维护抽象层、部署本地模型，这些都需要额外的工作量和费用。

你需要根据自己的业务场景来权衡：

  • 内部工具 / 玩具项目：单模型就行，挂了就等恢复
  • 一般产品功能：至少接 2 家模型，有简单的故障转移
  • 核心业务功能：多模型 + 健康检查 + 降级方案
  • 企业级 / 关键业务：完整的高可用架构 + 私有化兜底

这次故障之后，很多团队可能会重新评估自己的容灾等级。希望这篇文章能给你一些参考。
