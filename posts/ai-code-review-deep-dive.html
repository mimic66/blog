AI写了90%的代码之后：Claude Code 与淘宝的代码审查革命

2026-10-20 · 阅读约 18 分钟 · 标签：研发效能 代码审查 AI Native
核心问题 当 AI 生成代码占比从 10% 飙升到 90%，研发流程中最脆弱的环节是什么？不是写代码——代码已经快到产能过剩。是审查和测试。Anthropic 的 Claude Code 团队和阿里巴巴的淘宝体系，分别用两条路径给出了答案。

一、共同的困境：代码量翻倍，审查跟不上

两边的数据说的是同一个故事：AI 把编码效率拉了上去，但审查和测试变成了新的瓶颈。

Claude Code 团队的数据（来自 claude.dev 官方博客）：

  • Claude 写出了约 90% 的 Claude Code 自身代码
  • Anthropic monorepo 日变更量从 5 月的 2,500 次飙升到 9 月的 30,000+ 次
  • 6-9 月合并 PR 数量翻倍以上，回退率反而下降了 40%+

阿里巴巴的数据（来自《AI Native 研发范式实践手册》）：

  • AI 辅助编程普及后，代码产出呈指数级增长，但审查人力并未同步扩张
  • 引用 DORA 年度报告：代码 Bug 率 +9%，代码评审时间 +91%，平均 PR 体积 +154%
  • 淘宝闪购团队 AI 编码率从 9% 提升到 89.2%（2025.4-9月）
核心矛盾 产能的瓶颈，正在从"写"转移到"审"。通用 AI Review 工具能解决一部分问题，但因为缺乏领域知识和业务理解，在真正关键的代码上难以给出专家级判断。

二、Claude Code 团队的解法：七层滤网 + 风险分级

Claude Code 团队的思路可以用一句话概括：把审查从末端的一道门，变成连续的七层滤网。每一层各管一类问题，层层过滤，到最后需要人介入的就只剩最有价值的部分。

七层审查体系

层级 环节 核心动作
1 工作自验证（PR 前） 子 agent 在全新上下文 review diff；bug 搜索、diff 简化、E2E 检查技能并行运行
2 AI 审查（每个 PR） 多 agent 并行找 bug + 验证组投票过滤假阳性；按严重等级排序发布
3 安全审查 独立自动化流程，未解决的发现阻止合并
4 CI 硬性卡点 Lint、类型检查、多平台测试、构建
5 风险分级人工审批 低风险 0 人 / 中风险 1 人 / 高风险 2 人；分类器判定
6 合并队列 + 渐进发布 重新检查 + 功能开关 + 内部狗食 + latest/stable 分级
7 快速检测 + 快速回滚 开关秒级关闭；事故复盘追问哪一层本应捕获

关键设计：把人力按风险分配

最有意思的是第五层——按风险分级的人工审批机制：

风险等级 典型场景 所需人工审批
低风险 文档、文案、功能开关内的新功能 0 人
中风险 普通产品改动、缓存、系统提示词 1 人
高风险 计费、自动更新、CI 工作流 2 人

几个容易被忽略的细节：

  • 级别由改动内容决定，不由作者决定——再资深的工程师改计费代码也需要两个人审批
  • 只有 trusted author 能走低风险路径——主要是团队核心成员
  • 谁提的需求谁算一名 reviewer——agent 写的 PR，指挥 agent 的人承担一个审批位
  • 审批绑定具体 commit——新 push 了代码，审批就要重新给

质量进化的飞轮

Claude Code 团队把每一次线上事故都变成了评测集的一部分：

  • 每次事故/回滚都做成评测 case，reviewer 每天跑一遍
  • 任何对 reviewer 的改动（prompt、工具、模型）都要在这套集子上跑分验证
  • 噪音控制靠"看人怎么做"——reviewer 提的 comment 被修复了还是驳回了，用来校准误报率
  • 审查轮次上限 3 轮，之后要求作者退一步重思考；只对新 diff 做重审
效果数据 一轮审查通过率 65% → 78%；需 5 轮以上的 PR 8.9% → 1.5%；平均审查轮次 2.08 → 1.32。目标是大多数 PR 合并时最多 1 个人参与，且回退率和事故率不上升。

三、淘宝/阿里体系的解法：从通用审查到领域专家

阿里巴巴在 2026 云栖大会上发布的《AI Native 研发范式实践手册》中，提出了 Agentic CI（智能化持续集成） 四阶段模型，并以 Kitta 代码审查智能体为核心案例，展示了一条与 Claude Code 不同但殊途同归的路径。

Agentic CI：四个阶段的智能化升级

阶段 名称 核心变化
1 AI 协同编程 人机共写，编码不再受人力限制——产能激增
2 智能化代码评审 AI 从"辅助"变"主力守门员"，覆盖规范、架构、完整性、缺陷与安全
3 智能化测试 深度漏洞挖掘、补丁定向测试、安全补丁验证、回归与性能测试
4 人工审核合入 人从"逐行审查"退到"最终兜底"

Kitta：领域专用 Code Review Agent

Kitta 是手册中最有代表性的案例。它回答了一个关键问题：当通用 AI Review 不够专业时，怎么让 AI 像领域专家一样审查代码？

团队发现了三个核心痛点：

  1. 领域知识匮乏——通用模型见过很多代码，但未必懂内核的锁语义、编译器的中间表示约定
  2. 业务理解不足——"什么算问题、问题有多严重"，不同项目的标准截然不同
  3. 信任边界模糊——缺乏客观的质量评估标准和进化机制

Kitta 的"三步走"领域定制方案

第一步：构建项目级专家资产

  • 看得全（审查流程定制）——不同项目配置不同审查重点。回合补丁场景重点看语义一致性和变更完整性；API 项目重点看兼容性；发行版项目重点看集成风险
  • 看得深（领域知识定制）——沉淀多源分层领域知识库，审查时按模块、子系统自动匹配上下文，路由到对应的典型缺陷模式

第二步：确定性工程 + LLM Agent 混合架构

  • 规则能搞定的（NPE、SQL 注入等确定性安全规则）用规则拦，又快又准
  • 需要语义理解和上下文判断的，交给 Agent
  • 问题按严重程度分三级：Critical（内联评论，必须处理）、Medium / Low（仅提示）
  • 未发现风险直接给 LGTM

第三步：在线离线协同进化闭环

Kitta 与 Qwen 基座模型双向反哺，构建了一个持续积累的进化飞轮：

数据类型 内容 反哺目标
基准数据（Benchmark） 专家标注的基准数据集 漏洞发现能力——更深入的语义理解
审查轨迹（Trace） Agent 思维链轨迹跟踪数据 指令跟随能力——更准确的工具调用
用户反馈（Profile） 线上接受与拒绝的反馈 用户对话能力——更贴合的评审表达
代码改动（Code） 用户后续的代码修改动作 代码生成能力——更好的 Coding 与 Debug
Kitta 效果数据（来自手册） 累计审查 7 万+ 补丁，门禁准确率 97%，代码合入率稳定在 62%。已在操作系统内核、编译器、云原生平台等六大领域验证，实现 17.0%–31.6% 的审查质量提升。回合补丁场景一致性检查准确率 99.8%，采纳率 70.4%。

三条人机信任原则

手册专门总结了 AI Code Review 中人机协作的边界，这三条原则非常精炼：

原则一：精准分级，克制打扰 最好的 AI 门禁，不是把所有问题一股脑全抛出来——全量告警只会让开发者疲劳、麻木。高风险问题（安全漏洞、破坏性变更）坚决拦截 CI；一般性问题只作提示。考验的不是"报出多少问题"，而是"能不能把人类注意力留给最值得处理的风险"。
原则二：行为作证，拒绝自嗨 用户可能沉默，但代码变更骗不了人。不把开发者的默默无视当成认可，不看用户说什么，看"代码改了什么"。通过置信度熔断与追踪真实代码变更，基于客观变更驱动审查和模型迭代。
原则三：人类兜底，适时退场 AI 是探照灯，照亮风险、给出证据；人是方向盘，最终决策权在人。AI 在能发挥作用的地方尽可能前移、深入，在需要承担最终责任的地方适时退场。

四、测试环节的变革：从人写用例到 AI 全流程

审查只是第一道防线，测试是第二道。两边在测试侧的改造也呈现出相似的趋势。

Claude Code 团队的测试侧策略偏向工程化：

  • CI 扩展：每个 PR 运行数十项检查
  • 测试影响分析：只跑受改动影响的测试，应对 CI 压力
  • 合并队列重测：确保两个分别通过的 PR 不会合在一起把 main 搞挂

阿里体系的测试侧策略更偏向 AI 全流程自动化：

  • AI 生成测试用例：三层结构化知识库 + Prompt 工程 + RAG，C 端业务用例采纳率 85%+
  • 测试全流程自动化：需求解析 → 用例生成 → 数据构造 → 执行验证 → 对比校验，需求周期缩短 40%，AI 用例覆盖度超 70%
  • LLM-as-a-Judge 在线评测：六层 Rubric 标准 + 人工校准，实现日级质量监控
  • AI 产品评测平台：端到端评测为主、分层测评为辅，可回放环境 + 多裁判机制 + 变更分级策略

五、横向对比：两条路径，一个方向

维度 Claude Code 团队 淘宝/阿里体系（手册数据）

六、行业正在收敛的五条规律

两边的实践虽然路径不同，但都指向同一个结论。我们可以从中提炼出 AI 时代代码审查的五条新范式。

1. 审查从"一道门"变成"多层滤网"

不再是人读每一行代码，而是多层过滤——自验证、AI 审查、安全扫描、CI、分级审批——每层各管一类问题，层层递进。人只在最后兜底，处理最值得花时间的风险。这是从"门控思维"到"过滤思维"的转变。

2. 领域知识决定 AI Review 的上限

通用模型能解决 60% 的问题，但剩下 40% 的高价值问题需要项目级专家资产——知识库、缺陷模式、历史反馈。Kitta 的实践证明：领域定制能带来 17-31.6% 的审查质量提升，这是通用模型靠自身能力很难跨越的鸿沟。

3. 信任靠机制不靠感觉

AI 审查能不能真正用起来，关键不是模型有多聪明，而是有没有一套让人信得过的机制：客观评测集、行为数据追踪、分级处理、误报控制。Claude Code 的"事故即评测集"和 Kitta 的"行为作证"，说的是同一件事——用数据建立信任。

4. 进化飞轮是核心壁垒

线上真实数据 → 模型/规则优化 → 更好的审查 → 更多线上数据，这个飞轮转得越早，积累越厚。Claude Code 用事故驱动评测，Kitta 用四类数据反哺基座模型，本质都是构建越用越好的正循环。

5. 人的角色在升高维

从"逐行检查代码正确"变成"定义什么是正确、校准审查标准、对最终结果负责"。工程师不再是代码的作者，而是 AI 的训练师和质量的最终裁判。这不是简单的效率提升，而是角色的重新定义。

最后的判断 当 AI 编码率从 10% 走向 90%，研发体系中最需要重新设计的不是编码环节，而是质量保障体系。代码审查正在经历一次从"人工逐行"到"AI 主导 + 人类兜底"的范式转移。谁先把这个飞轮转起来，谁就能在 AI 时代获得真正的质量优势——而不是仅仅获得速度优势。
