Anthropic Scion 深度剖析：为 AI Agent 重写的版本控制系统

2026-10-23 · 阅读约 16 分钟 · 标签：Scion 版本控制 Anthropic 架构设计
背景 2026 年 10 月 13 日，Anthropic 发布了一篇石破天惊的文章：他们用 5 个月时间，从零构建了一套内部版本控制系统 Scion，并完整迁移了整个 monorepo。原因很简单——Git 顶不住了。日均合并量从 5 月的 2,500 次涨到 9 月的 30,000+ 次，涨了 12 倍。Git 的分布式设计，在 Agent 大规模写代码的时代，反而成了瓶颈。

一、为什么 Git 顶不住了？

在讲 Scion 之前，我们得先搞清楚：Git 到底哪里不行了？

Git 是为人类开发者设计的分布式版本控制系统。它的核心设计假设是：

  • 每个开发者都有一份完整的仓库副本
  • 开发者可能离线工作，需要本地完成 diff、blame、历史查看
  • 一天提交几次，一次提交改几十到几百行

这些假设在 AI 时代全部失效了。

三个致命瓶颈

1. 体量爆炸：仓库大到搬不动

Anthropic 的 monorepo，仅 main 分支的历史就接近 100 GB，压缩后的工作副本超过 25 GB。CI 每天要执行约 2,500 万次代码检出（还没算开发者环境、Agent 沙箱和研究任务）。如果直接 fetch，一天就是 600 PB+ 的 Git 流量。

600 PB 是什么概念？大概是整个互联网日均流量的几十分之一——只是为了检出代码。

2. 镜像策略走到了尽头

Anthropic 一开始用的是业界标准做法：内部 Git 镜像 + 仓库快照（seeds）存在 blob 存储里。高峰期他们运营了几百个内部 Git 镜像来扛负载。

但这个方案有天花板：镜像的磁盘和内存上限到了，就加不上去了。而且快照离 main 分支 tip 越来越远（因为合并太快了），依赖完整历史的操作（diff、blame）在部分克隆上越来越难维护。

3. 分布式特性反而是负担

最根本的问题是：Anthropic 发现他们实际上是把 Git 当中心化系统在用——有一个权威副本，几乎所有客户端都是 Agent 和 CI 任务，天然在线。

Git 为分布式、离线工作设计的那些特性（完整本地副本、packfile、本地计算 diff/blame），在 Agent 在线的场景下，反而成了扩展性的阻碍。

核心洞察 当写代码的主体从人变成 AI，版本控制系统的设计假设就变了——从「人离线、少提交」变成「Agent 在线、海量提交」。Git 的分布式优势，在这个新场景下，成了它最大的劣势。

二、Scion 的六大设计原则

想清楚了 Git 的问题，Anthropic 团队问了自己一个问题：如果从一开始就知道客户端永远在线，版本控制系统应该长什么样？

于是有了 Scion 的六大设计原则。每一条，几乎都是对 Git 设计哲学的反转。

原则一：客户端永远在线

Git 假设客户端离线工作，需要完整仓库副本。Scion 假设客户端（Agent 和 CI 任务）永远在线，需要数据时才向服务器取，不提前下载整个仓库。

这是最根本的设计转向，其他所有原则都从这一条衍生出来。

原则二：客户端-服务器不对称

Git 里每个客户端都是完整的服务器——能算 diff、能看 blame、能合并、能 rebase。

Scion 里，服务器和客户端是完全不对称的：

  • 服务器做：文件历史、blame 查询、创建提交、执行合并和 rebase
  • 客户端做：有限的本地对象缓存、把工作副本铺到磁盘上、监控文件系统变化、提供用户交互界面

客户端自己几乎算不了什么——但作为交换，它本地需要的数据量也小得多。

原则三：版本控制是一项服务，可以支撑各种应用

Git 时代，CI 任务想知道「谁最后改了这一行」或者「两个 commit 是什么关系」，要么本地拉个仓库，要么指望平台提供的 API。

Scion 把所有源控制查询都做成了 API——很多时候任务根本不需要本地仓库。Anthropic 的自动化二分查找（bisect）和回滚流水线，就是完全靠 API 跑的，在以前的规模下根本不现实。

这是一个很重要的范式转变：版本控制从「一个工具」变成了「一项基础设施服务」。

原则四：一切都要水平扩展

Git 镜像方案的问题是「有顶」——镜像的磁盘和内存有上限，到了就加不动了。

Scion 的数据是分布式的，每个组件都可以独立扩展。服务器上也没有完整物化的仓库副本，没有类似 Git packfile 的东西，也就不需要仓库维护（比如 git gc）。

原则五：提交要便宜、增量、无锁

Git 里你本地提交，然后 push 上去共享。Scion 里每次提交、rebase、合并都在服务器上发生，所以这些操作必须足够快。

关键约束是：创建提交和更新下游数据结构的成本，要跟变更的大小成正比，而不是跟整个仓库的大小成正比。不然服务器扛不住。

还有一个很有意思的设计决策：Scion 刻意不鼓励用分支（ref），除了 main 和 release 分支。因为全局指针（每个服务器都要达成一致的 ref）是扩展的天敌。

原则六：工作副本是可选的，而且天生稀疏

既然仓库这么大，CI 每天又要检出几千万次，能不检出就不检出。

  • 只需要 commit 和 merge base 的 diff？直接问服务器要，不用 checkout
  • 很多写操作也可以完全走 API，不用工作副本
  • 即使要检出，也是稀疏检出（sparse checkout）——只拿你要的目录
  • 更激进的是虚拟化检出（virtualized checkout）——按需物化文件，读了哪个文件才加载哪个

三、Scion 怎么工作：核心数据结构与架构

原则讲完了，我们来看看具体是怎么实现的。

Changeset：Scion 的提交单元

Scion 的核心数据结构叫 changeset，相当于 Git 里的 commit，但存储方式完全不同。

Git commit Scion changeset
存储内容 指向整棵树的指针（tree hash） 相对于第一个父节点的「变更文件列表」
创建位置 本地创建，然后 push 服务端创建，立即可全局访问
写入方式 写入 packfile，需要 gc 维护 写入预写日志（WAL），增量追加

这个设计的好处是：

  • 写入吞吐量极高——没有 packfile 要接收，没有跨服务器协调，没有 ref 要移动
  • 锁粒度极细——changeset 是 WAL 里的一条记录，追加写入即可
  • 成本跟变更量成正比——小变更就是小 changeset，大变更就是大 changeset，不会因为仓库整体大就变慢

当然也有代价：只存变更的话，单独一个 changeset 回答不了「谁改了这一行」「哪些 commit 影响了这个文件」这种问题。所以 Scion 在此之上构建了衍生数据结构。

衍生数据（Derived Data）：按需构建的索引

为了回答 blame、文件历史、提交图关系这类问题，Scion 从 changeset 出发构建各种衍生数据结构——包括文件 blame 专用结构、路径历史结构、提交图的跳表等。

所有衍生数据都通过一套通用机制计算：每种衍生数据是递归定义的，它在某个 changeset 上的值，是从它在该 changeset 父节点上的值算出来的。

这套机制有三个好处：

  1. 易扩展——需要新的索引加速某个操作时，加一种衍生数据类型就行
  2. 懒计算——每种数据可以选择提前算还是延后算，不需要的就不物化，节省空间
  3. 对客户端透明——客户端看不见这些数据结构的内部，团队可以随时优化它们而不影响客户端

这是一个非常优雅的设计：核心只存最基本的变更信息，其他所有索引都是可丢弃、可重建的衍生数据。

三层缓存架构：从服务器到节点

Scion 最精妙的部分可能是它的检出（checkout）架构。不是简单的客户端-服务器两层，而是三层：

Scion 三层架构
scion-server（权威服务器） → scion-cache（区域缓存服务器） → scion-daemon（节点本地守护进程） → 客户端

每一层都响应相同的 RPC 协议，客户端根本不知道自己在跟哪层对话。但每一层都有明确的职责：

  • scion-server：权威数据来源，从 Spanner 和云存储读取数据，计算衍生数据
  • scion-cache：区域缓存服务器，从内存直接流式返回对象（磁盘格式跟 daemon 消费的格式一致），命中时不需要计算
  • scion-daemon：每个计算节点上跑一个，存储本节点共用的对象。同一节点上的多个任务共享大部分相同的对象

为什么是三层而不是两层？因为故障隔离——严格分层是为了防止级联故障。如果某个区域的 cache 挂了，不能让它把上游的 server 也打挂了。

每层缓存命中率都在 99% 以上，而且不需要长期状态，扩容很容易。

检出协议：Git packfile 的反面

Git 的检出协议是这样的：客户端告诉服务器「我有什么」，服务器算出差集，打一个大包发回来。单次大响应、delta 压缩、效率很高——但前提是客户端有大量本地数据。

Scion 的协议完全反过来：客户端不说自己有什么，只说自己要什么——从根树开始，先检查本地缺少哪些树对象，递归请求，然后再对 blob 做同样的事。

每个请求都是针对一个永不改变的具体对象（内容寻址），所以任何缓存层都能直接应答。架构上跟传统的分层缓存非常像。

这种设计的好处：

  • 高效且可恢复——没有单个几 GB 的 packfile 响应，断了续传就行
  • 稀疏检出天生支持——不要的树就不请求，不需要特殊支持
  • 虚拟化检出也容易——读了哪个文件才请求哪个

四、效果数据

讲了这么多设计，效果到底怎么样？

指标 Git 镜像方案 Scion 提升
基础设施占用（CPU/内存） 基线（几百个镜像） — 缩小 200 倍
CI 检出速度 分钟级 秒级 快 100 倍
CI CPU 容量释放 — — 节省 25%
仓库维护 需要定期 gc / 重新打包 不需要（客户端和缓存都不需要） 运维成本大幅降低
构建团队规模 — 7 人团队 + Claude 辅助 5 个月完成 + 完全迁移

7 个人、5 个月，从零写了一个版本控制系统 + 代码审查工具（Antique）+ 半打相关系统，还完成了全量迁移——期间代码合并量还涨了 10 倍。这个速度在以前是不可想象的。

五、Scion 的适用场景和不适用场景

Scion 很厉害，但它不是 Git 的替代品。Anthropic 自己也明确说了：Scion 不适合作为通用 Git 替代品。

什么时候该用 Scion 式的架构？

Scion 的设计在以下场景中优势最大：

适用场景
  • 超大 monorepo（几十 GB 以上）
  • 极高的提交频率（每天几千到几万次合并）
  • 大量 CI/Agent 检出任务（每天百万次以上）
  • 客户端基本都在线（不需要离线工作）
  • 需要程序化地查询版本控制信息（blame、diff、历史）

典型的公司：Google（有 Piper）、Meta（有 Sapling/Mononoke）、Anthropic，以及未来 AI Agent 大规模写代码的公司。

注意一个有趣的趋势：这些公司都是 monorepo 模式。Scion 的设计跟 monorepo 是深度绑定的——只有在单一大仓库的模式下，「集中化服务 + 海量检出」的架构才划算。

什么时候不该用？

不适用场景
  • 中小规模仓库（几 GB 以下）——Git 完全够用，Scion 反而过度设计
  • 需要离线工作的场景——Scion 客户端离开服务器几乎什么都干不了
  • 开源社区协作——Git 的分布式特性正是开源协作的基础
  • 多仓库模式——Scion 的优势来自集中化，分散的小仓库用它反而重

Anthropic 自己也说，不打算把 Scion 做成公共产品。原因很实际：迁移成本太高了——不只是版本控制系统本身，还有代码审查、代码搜索、CI 等等全套工具链都要换。

六、更深的启示：Agent 时代的研发基础设施

Scion 这个项目最有价值的地方，不是它的技术细节有多牛，而是它揭示了一个更宏观的趋势：当 AI 开始大规模写代码，整个研发基础设施栈都需要被重新设计。

版本控制只是第一个倒下的多米诺骨牌。

合并队列还有意义吗？

Anthropic 在文章里提了一个很有意思的观察：在 Agent 规模下，传统的合并队列（merge queue）不太有意义了。

为什么？因为测试跑一遍的时间里，可能已经有几百上千个变更合入了。你怎么排队？全局锁的话吞吐量完全不够。

他们的应对方式是：投资于合并后 + 部署前的自动化测试。并发变更可能会冲突，但 Claude 修复冲突的速度，比人类发现冲突还快。

这是一个非常颠覆的思路：不再追求合并前 100% 没问题，而是接受合并后可能有问题，靠快速检测和快速修复来兜底。

CI 的定义变了

传统 CI 的概念是「提交代码 → 跑测试 → 通过才能合并」。但在每天几万次提交的规模下，等测试跑完再合并，队列会无限长。

那 CI 还有意义吗？有，但形态变了：

  • 从「合并前的门」变成「合并后的网」
  • 从「全量测试每一个变更」变成「按风险分层测试 + 定向测试」
  • 从「保证不出问题」变成「快速发现问题 + 快速回滚」

工程师的角色变了

Scion 团队 7 个人 5 个月完成了以前几十人几年的工作量。他们自己总结说：团队里每个工程师都觉得 Claude 写代码比自己强，但工程师的价值并没有降低——只是变了。

工程师现在提供的是：

  • 对系统间高层组件关系的理解
  • 设计层面的权衡判断
  • 对「要解决什么问题」和「要达到什么规模」的清晰定义
  • 对 Agent 说「不」的能力——Agent 经常会违反核心系统约束，工程师要把它拉回来

审查也从「逐行读代码」变成了「审查变更的意图」。

运维也变了：Superfan 模式

Scion 团队还分享了一个很有趣的运维模式——他们叫 Superfan（超级粉丝）。

给每个核心组件配一个 Claude，让它 7x24 小时盯着那个组件的监控和日志，像一个只关心这一件事的资深工程师，不停刷新图表找异常。

传统告警是一维的（阈值触发），Superfan 能发现更微妙、更新颖的问题。

这可能是 AI 时代运维的新形态：每个组件有一个专属 AI 运维工程师，人类运维团队处理真正复杂的情况。

七、对行业的影响

Anthropic 明确表示不打算开源 Scion 或者做成产品，但这不意味着这篇文章只有八卦价值。恰恰相反，它的价值在于给整个行业指了一个方向。

Anthropic 自己也在文章最后呼吁：GitHub、GitLab 和开源社区可以从这些思路里借鉴，让 Git 在不抛弃整体模型的前提下，也能支撑 Agent 规模的负载。具体来说：

  • Git 服务器不一定非得跟 Git 客户端工作方式一样——可以有新的服务器架构
  • Git 平台可以提供全面的服务端 RPC（就像 Scion 一样），甚至可以跨 forge 标准化
  • negotiation 协议不一定非得是现在这样——sparse、shallow 这些特性可以更好地组合

换句话说：Git 的客户端体验可以保留，但服务端需要被重新设计。这可能是未来几年 Git 平台（GitHub、GitLab、Gitee 等）的主要进化方向。

一句话总结 Scion 不是一个更好的 Git，它是一个为 AI Agent 时代设计的版本控制系统。它的真正意义不在于技术细节有多酷，而在于它用一个极端案例证明了：当写代码的主体从人变成 AI，研发基础设施栈的每一层——从版本控制到代码审查到 CI 到运维——都值得被重新思考。
